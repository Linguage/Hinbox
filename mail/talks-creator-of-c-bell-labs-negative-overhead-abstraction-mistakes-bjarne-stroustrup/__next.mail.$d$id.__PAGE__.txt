3:T15aeb,<h2>访谈概述</h2>
<p>本期访谈邀请到了 C++ 编程语言的创造者、前贝尔实验室研究员 Bjarne Stroustrup。在对话中，Bjarne 回顾了 C++ 的诞生历程以及在传奇的贝尔实验室的工作岁月，并分享了关于他与 Dennis Ritchie（C语言之父）的交往回忆。</p>
<p>此外，访谈深入探讨了编程语言设计的哲学（包括强类型系统、内存安全、垃圾回收机制等）、C++ 标准委员会的运作内幕、零成本抽象与性能优化的权衡，以及他对当前大语言模型（AI）自动生成代码的看法。在节目的最后，Bjarne 还针对自己广为流传的几句编程名言进行了解读，并分享了如果能回到过去，他会给自己的几条核心建议。</p>

<h2>访谈正文</h2>
<p><strong>Bjarne Stroustrup</strong>：当时世界上没有任何一种语言能够满足我的需求。</p>
<p><strong>Ryan Peterman</strong>：这位是 Bjarne Stroustrup，C++ 的创造者。我们聊到了他的职业生涯，从贝尔实验室讲起。是什么让你有信念自掏腰包飞去那里的？</p>
<p><strong>Bjarne Stroustrup</strong>：那是世界上最好的地方，对吧？我还需要别的理由吗？</p>
<p><strong>Ryan Peterman</strong>：我还向他请教了关于编程语言设计的问题。实现过程中技术上最具挑战性的是哪一部分？</p>
<p><strong>Bjarne Stroustrup</strong>：每个人都会问这个问题，但我认为这问错了。</p>
<p><strong>Ryan Peterman</strong>：我通常认为，更多的抽象会带来性能上的损耗。</p>
<p><strong>Bjarne Stroustrup</strong>：并不是这样。我们可以做到负成本抽象（Negative overhead abstraction）。</p>
<p><strong>Ryan Peterman</strong>：回过头看，有没有哪一部分让你觉得“噢，那是个错误，我当时应该更加坚持我的立场”？</p>
<p><strong>Ryan Peterman</strong>：以下是完整节目内容。C++ 诞生的起源故事是怎样的？</p>
<p><strong>Bjarne Stroustrup</strong>：让我们从真正的开端讲起。我在贝尔实验室找到了一份工作，那是在新泽西州一个非常棒的地方。现在那里已经大不一样了，但在当时，它是世界上最好的应用数学和应用工程机构。我环顾四周，看到那里有非常多伟大的人。他们构建了 Unix，构建了 C 语言，还做了大量背后的理论工作。</p>
<p>我意识到，我必须做点重要的事情，否则我就不属于这里。所以我决定要构建一个分布式 Unix，因为很明显计算机在变得更好，网络在变得更好。所以我们需要这样一个东西。</p>
<p>如果我成功了，我们可能就会提前 10 年拥有 Unix 集群之类的高级技术。但当然，我没能做成。那不是一个人能完成的工作。不过我首先意识到的是，当时世界上没有任何一种语言能够满足我的需求。它需要具备两个条件：一是对硬件的底层访问能力，以便处理内存管理器、进程实现、进程调度器、网络驱动程序、设备驱动程序等等；二是对高层抽象的支持，比如要表达“这台计算机上有个模块，那台计算机上也有个模块，这是它们使用的通信协议”之类的事情。有很多语言能做到其中之一，但没有一种能同时做到这两点。</p>
<p>用于底层操作的明显选择是 C 语言，因为 Dennis Ritchie 和 Brian Kernighan 就在走廊那头。我说“分布式 Unix”，是因为我正身处于 Unix 被发明并持续开发的大本营。</p>
<p>至于高级语言，当时也有不少，但它们都太慢了，而且无法操作硬件。不过我学过使用 Simula。我认识发明了面向对象编程和 Simula 的 Kristen Nygaard 和 Ole-Johan Dahl。所以我决定必须将这两者结合起来。</p>
<p>当时切实可行的方法是，将 Simula 中的“类（class）”概念引入 C 语言中，这样它就能运行得非常非常快，并且可以用于系统编程。</p>
<p>同时，我让类型系统变得更加规范。用户自定义类型（类）的处理方式与内置类型相同，这基本上就是 C 语言和 Simula 都做不到的事情。这在很多年后最终促成了泛型编程（Generic programming）。我不得不添加重载功能。我们一直都有重载——你可以把整数相加，也可以把浮点数相加，甚至可以用一个加号把浮点数加到整数上，这是一个通用的名字。所以我必须将其泛化，以便为内置类型和用户自定义类型提供一套统一的规则。这就是 C++ 的由来。</p>
<p><strong>Ryan Peterman</strong>：我看过你的一场讲座，你在里面提到曾用 BCPL 重写过一个模拟器。那是分布式 Unix 的工作吗？</p>
<p><strong>Bjarne Stroustrup</strong>：不，那是在更早之前。我去英国剑桥读博士，在某个时候我决定需要为分布式系统编写一个模拟器，以完成我的博士研究。当然，三四年后分布式 Unix 的想法也是源于同样的思维方式。</p>
<p>当时，我用 Simula 写了一个非常棒的模拟器。Simula 非常擅长做这个。它的名字起得不好，因为它其实是一种通用编程语言，这个带有局限性的名字对它毫无帮助。总之，我写了这个模拟器，写了小示例、测试用例等等，一切都运行得很好。然后我尝试了第一次真正的大规模全面运行，占用了系里大型机相当长的计算时间。</p>
<p>博士生是不能这么做的。化学家和天体物理学家们绝不会接受这种资源占用。所以我被赶下了机器。很明显，我可以用 Simula 写程序，但我负担不起运行它的成本。</p>
<p>所以我带着这些想法，把程序转移到了一台鲜有人用的实验性计算机上，那是 CAP 计算机。它有硬件保护机制和权能系统（capabilities），非常适合做硬件研究，但也有些不同寻常。那些天体物理学家用不了，他们不是纯粹的计算机科学家，但我可以用。</p>
<p>唯一的问题是，我不能在上面运行 Simula，因为 Simula 从未被移植到那种机器上，它主要在大型机上使用，而且是专有的，在 CAP 计算机的环境下一切都不对口。</p>
<p>所以我基本上用 BCPL 重写了我的模拟器。BCPL 这种语言会让 C 语言看起来都像是一门高级语言。它仿佛只有一种数据类型——“字（word）”。那是一次非常痛苦的经历，但一旦我完成了，我的程序运行速度估计快了 50 倍。我得到了我的数据，也拿到了我的博士学位。</p>
<p>这很好。但我当时就确信，我绝不会再用在剑桥大型机上用过的那种极其低效的工具来尝试解决问题了。所以我列了一个清单，列出了我理想中的语言应该具备哪些特性。C++ 并没有完全包含所有特性，但它比现存的任何其他语言都更接近理想状态。C++ 就是从那里诞生的。</p>
<p><strong>Ryan Peterman</strong>：在那场讲座中你还提到，用 BCPL 写那个程序太困难了，为了调试你掉了一半的头发。</p>
<p><strong>Bjarne Stroustrup</strong>：这几乎是千真万确的。而在这些年里，为了让 C++ 步入正轨，我把剩下的一半头发也掉光了。但不管怎样，它成功了。</p>
<p><strong>Ryan Peterman</strong>：你提到了贝尔实验室，我想大家对这个话题都有很多好奇心，因为那是一个非常传奇的地方。当你博士毕业，在考虑去哪里工作时，在社交和文化层面上，贝尔实验室当时的名声是怎样的？</p>
<p><strong>Bjarne Stroustrup</strong>：如果你想在世界顶尖的平台上进行大规模的实际工程开发，贝尔实验室就是不二之选，我认为它绝对是当时最好的。可能我们那里的计算机科学家数量是当时麻省理工学院（MIT）的两倍。计算机科学研究中心汇聚了非常棒的人才，其中一些人来自剑桥。</p>
<p>我在剑桥的最后一年，有一天贝尔实验室的一个人来做讲座。在英国和计算机实验室的传统是，一天工作结束后，你会去酒馆和其他人聊天，看看最近都在忙什么。他对我说：“当你需要工作的时候，给我们打个电话。”所以我照做了。</p>
<p>实际上我是自掏腰包飞去新泽西的。我后来的老板，做网络研究的 Sandy Fraser——他是个很棒的人——告诉我，我来得不是时候。他们没有职位空缺了。</p>
<p>当你刚刚飞越了整个大西洋，这绝对不是你想听到的话。不管怎样，第二天我在一个开发团队（而不是研究团队）做了一场技术分享，然后他们改变了主意，把我带到了研究团队。在那之后的几十年里，我一直在那里工作。</p>
<p><strong>Ryan Peterman</strong>：当时的面试流程是怎样的？</p>
<p><strong>Bjarne Stroustrup</strong>：就是和一些人聊聊天。我记得和 Dennis Ritchie 聊了很久，我还和做网络的人聊了聊。其实并没有什么正式的面试流程。他们已经有五年没有招新人了，所以完全是凭直觉在做决定。</p>
<p><strong>Ryan Peterman</strong>：所以这有点像建立在信任和其他人的背书上？比如 Dennis Ritchie 跟你聊过，他觉得你懂行，Sandy Fraser 他们和你交谈，看看你懂什么、不懂什么。</p>
<p><strong>Bjarne Stroustrup</strong>：对，最后他们去见总监，说：“在这个案子上，我们找到了个不错的小伙子，你能批给我们吗？”我当然对这些一无所知。我当时已经去了加州和别人在聊了，然后接到了总监的电话说：“你愿意一周后来这里工作吗？”</p>
<p><strong>Ryan Peterman</strong>：在甚至还没有工作承诺的情况下，是什么信念让你自掏腰包飞过去的？</p>
<p><strong>Bjarne Stroustrup</strong>：那是世界上最好的地方，对吧？还需要更多理由吗？</p>
<p>如果成功了，那就是最好的去处；如果不成功，那又怎样？你不可能在每件事上都成功。今天，很多其他行业有更强的吸引力。</p>
<p><strong>Ryan Peterman</strong>：在那个时候，比如 IBM 之类的地方会是业界最好的吗？</p>
<p><strong>Bjarne Stroustrup</strong>：我跟 IBM 谈过，他们不如贝尔实验室的计算机科学研究中心好。我去了约克镇高地（Yorktown Heights），和他们的研究人员以及年轻的研究员交谈过。我就是觉得他们做的东西不对路，方式也不对。相比于贝尔实验室的研究员，他们受到了多得多的控制和指令。</p>
<p><strong>Ryan Peterman</strong>：在贝尔实验室这样的地方，项目选择是如何进行的？一旦你被录用，这一切是如何运作的？</p>
<p><strong>Bjarne Stroustrup</strong>：在当时，甚至我想现在也是如此，要做出好的研究有两种哲学。一种是管理层和高层精心挑选一个设计周密的重点项目，投入充足的资金，指派二三十个人去解决这个问题，最后做出伟大的成果。</p>
<p>另一种哲学是，雇佣你能找到的最优秀的人，然后不要告诉他们要做什么。当时给我的工作职责描述是：“在一年内做点有趣的事情。然后告诉我们你做了什么，如果我们觉得不错，明年就继续给你同样的待遇。顺便说一句，你的汇报方式是写满一张纸，字号不能小于9号。因为如果你不能简洁地说明你做了什么，你做的东西可能就不够有趣。”这非常与众不同。</p>
<p>所以当他们构建 Unix 时，实际上还在担心，因为它最终涉及了五到七个人，对于这种“个人做有趣事情”的模式来说，规模变得太大了。</p>
<p>这是非常不同的。我想说，总体而言，这种相当无政府主义的组织结构比那种组织严密的模式表现得更好。你听说过的大部分出自贝尔实验室的东西，都是从这种模式中诞生的。在同一栋楼的其他区域，他们还在做硬件。我们今天使用的光纤就是从那里出来的。很多无线电技术也是。作为相机核心的电荷耦合器件（CCD）也是从那里出来的。他们尝试做视频电话，虽然没能成功，因为当时的硬件还跟不上，但他们确实在尝试。用于手机的蜂窝网络系统也是出自贝尔实验室的另一栋楼。那真的是个很棒的地方。</p>
<p>所以计算机科学的人倾向于和其他领域的人交流。我记得当时我在做模拟研究，我帮助过一个人构建用于网络研究的模拟器。早期 C++ 的很多工作都与解决诸如“网络过载时会发生什么”、“我们如何处理过载协议”等问题有关。</p>
<p>在这个特定的案例中，他们做得很好。后来他们又把我叫回去，他们有一个稍微大一点的问题：他们想模拟曼哈顿的计算机流量。即便是那时，我的回答也是：“不，我们没有足够的计算能力来做这个。不管 C++ 有多好，现在的计算机都做不到。”</p>
<p><strong>Ryan Peterman</strong>：那是过去，现在他们可能做得到了。</p>
<p><strong>Bjarne Stroustrup</strong>：也许吧，但当然现在的计算机流量也变得极其庞大了。所以也许他们还是做不到。我现在手头没有数据。但当时他们给了我数据，这就是我拒绝帮助他们的原因，因为那是不可能的。</p>
<p><strong>Ryan Peterman</strong>：我在做研究时看到，你曾提到连续 16 年左右，你每周都会和 Dennis Ritchie 一起吃午饭。他也是一个非常传奇的名字。我很好奇，有没有什么你从他那里学到的东西，或者让你印象深刻的事情，可能影响了你或 C++？</p>
<p><strong>Bjarne Stroustrup</strong>：他是个很棒的人，我们聊了很多东西。他从来没有说过任何关于 C++ 的粗鲁或负面的话。实际上，在他的 HOPL（编程语言历史会议）论文中，他指出 C++ 是 C 语言显而易见的继任者。所以，所有那些“C 与 C++ 的语言之争”都是荒谬的。</p>
<p>这些争论本不该发生，而且也绝不是因为我们之间有矛盾，因为我认识 Dennis。我们并没有在打架。我至今仍认识 Brian Kernighan，这周五我还和他聊了天。我们是好朋友，所谓的语言之战真的很愚蠢。</p>
<p>Dennis 曾帮助我在 C++ 中设计了 <code>const</code>。它以前被称为 <code>read-only</code> 和 <code>write-only</code>，但做 C 语言的人觉得两个单词处理起来很麻烦，而且太长了。所以最后我们得到了现在这个关键字，这是我记得的具体的一件事。Dennis 很有帮助。</p>
<p>他当时对函数重载有点担心，因为你必须先查看函数的声明，才能知道一次函数调用的确切含义。但那是一种非常可执行的思维方式。事实证明它运行良好。今天任何写 C 语言的人，实际上都在使用我的心血，因为现代的函数定义、函数声明以及调用语义的语法，都是从我早期的 C++（带有类的 C）工作中诞生的。</p>
<p>所以当人们开始抱怨时，他们应该记住，他们其实每天都在使用我设计的东西。（笑）</p>
<p><strong>Ryan Peterman</strong>：你写过一些非常详尽的，几乎像是 C++ 历史记录的文章，可能是在某个会议上发表的那三篇长篇论文。在其中一篇里，有一个关于 Dennis Ritchie 的轶事。是关于他向 C 标准委员会提出了“胖指针（fat pointer）”的概念，也就是指针本身也存储它所指向的数组大小。你提到 C 委员会没有批准，我很好奇你能否讲讲这个故事？</p>
<p><strong>Bjarne Stroustrup</strong>：Dennis 虽然创造了 C 语言，但他并没有参与标准委员会。我甚至听 C 标准委员会的人说：“不，Dennis 不是 C 语言专家。他从没来开过会。”这种态度非常奇怪，但不管怎样，我们当时就意识到了缓冲区溢出（buffer overflow）和越界错误的问题。显而易见的解决方案就是使用 Dennis 所谓的“胖指针”，即指针加上它所指向的元素数量。</p>
<p>但这需要占用两个字（word）的内存。这大概也就是早期 C 语言不使用它的原因——那时他们只有 48K 的内存。当我和 Dennis 讨论这个的时候，我想我们大概有了整整一兆（1 MB）的内存。而当我刚开始做 C++ 时，我们只有 256 KB。我知道我们迟早会有一兆内存，所以我们在讨论。他称之为胖指针，而今天在 C++ 中，它们被称为 <code>span</code>。</p>
<p><code>span</code> 源于我与其他人合作编写的《C++ 核心指南》（C++ Core Guidelines）的工作。我们需要这样的机制，如果没有它，我们就无法提供所需的控制和安全程度，所以我们构建了 <code>span</code>，稍后它被纳入了标准。但这些想法中的一些已经非常古老了。</p>
<p><strong>Ryan Peterman</strong>：当你被世界上最杰出的人包围时，看着周围人有多么伟大，即使每个人本身也很优秀，这种别人的伟大有时会让人产生一种“冒名顶替综合征（imposter syndrome）”。这也是你在贝尔实验室曾经感受到或看到过的吗？</p>
<p><strong>Bjarne Stroustrup</strong>：绝对有。也许我现在还有点。但肯定的是，当我来到贝尔实验室，看到门上的名字，那些我读过他们论文、开创了我喜欢的研究领域的人都在那里。是的。我觉得我必须提升自己的水平。我必须做点比我原先设想的更大更好的事情。</p>
<p>而且，你和他们交谈，你会学到东西。我的意思是，在午餐时我学到了很多。当时有一群人在一起聊他们在做什么，以及为什么这么做。</p>
<p>有些地方能对人产生这种影响，拥有极高的人才密度。剑桥大学的计算机科学系就是这样的地方之一。我在那里学到了很多。而且，门总是敞开的。这几乎成了一项政策——我们保持门敞开，否则别人怎么能进来和你交谈呢？</p>
<p><strong>Ryan Peterman</strong>：当我们谈论编程语言以及语言设计时，如果我今天想构建一门编程语言，要将其变为现实，我需要构建哪些部分？</p>
<p><strong>Bjarne Stroustrup</strong>：这是个相对容易回答的问题，而且每个人都会问。但我认为这问错了。你需要的是一个需要解决的“问题”。很多人只是想构建一种在他们当前工作或他们关心的特定领域比现有工具更好的语言。在大多数情况下，用现有的语言已经能做得相当好了。</p>
<p>如果你构建的是一门非常专业的领域特定语言，那很好。但如果我们谈论的是更通用的语言，当你希望与其他人合作时，它对别人来说就不一定是理想的。</p>
<p>有时候有人会问我为什么 C++ 这么庞大、这么复杂。有两个原因。一个是历史原因。由于种种限制，我无法在 80 年代直接构建出我想要的 C++。部分原因是技术水平，部分原因是计算机性能，还有部分原因是我懂的还不够多，我必须学习。所以你采用了标准的工程做法：尽你所能做到最好，然后看看什么行得通、什么行不通，尝试修复问题，然后循环往复。</p>
<p>这就是 C++ 发展的方式。因此，里面残留了一些遗留的东西，有时会碍事。现在你们有了 <code>span</code>，就很少需要使用指针了，更不应该把指针当成资源句柄来使用。在 1979 年的带类的 C 语言中这就已经内置了，但人们没有领会。所以还有很多教育工作要做。</p>
<p>但是，一旦你发现自己有一个需要新语言来解决的问题，你就开始看现有什么。你有很多辅助资源，很多关于词法语法分析和代码生成的书籍。你还有像 LLVM 这样的框架，大多数现代语言都在使用它来生成高质量的代码。所以，大多数与 C++ 竞争的语言，实际上是使用 C++ 的基础设施来实现的。这非常有趣。</p>
<p>总之，首先要关注“问题”，不要以为你是唯一的用户。如果你认为你是唯一的用户，你构建的就是特定用途的编程语言，那没关系。当你为合适的问题找到合适的解决方案时，领域特定语言（DSL）是非常棒的。但首先要明确问题。</p>
<p>在我的情况下，问题是：我需要在同一种语言中同时具备高层抽象和底层控制。否则，我就得使用两种语言，并想办法让它们正确通信。当时的高级语言往往采用会牺牲性能的接口。很多时候它们需要垃圾回收机制，这对于设备驱动程序，或者对于编写垃圾回收器本身来说，是非常不友好的。所以，明确问题，然后尝试解决它。</p>
<p><strong>Ryan Peterman</strong>：当年你创建 C++ 并明确了问题，然后着手构建它。里面有很多组件，对吧？有编译器、链接器，在这些实现里还有解析器（parser）、词法分析器（lexer）等等。在构建最初版本时，技术上最具挑战性的部分是什么？</p>
<p><strong>Bjarne Stroustrup</strong>：我不认为有哪一部分是特别具挑战性的。难点更在于，正如你指出的，部分太多了。我做出的一个后来引起麻烦的决定是：我不打算碰“链接器（linker）”。</p>
<p>这仅仅是因为我四处打听了一下，发现单单在贝尔实验室，人们就使用了大约 25 种不同的链接器。如果我想服务于我最初的目标用户，我就必须编写 25 个链接器的接口或修改它们。而没人希望你去碰他们的链接器，因为一旦你搞错了，所有东西都会崩溃。</p>
<p>所以我定下了一个规矩：别惹链接器。后来人们确实修改了链接器，使之更适合 C++，但那是在 C++ 已经成为主流语言之后的事了。</p>
<p>另一件事是，当时有很多不同的优化器。不同来源的计算机都有不同的优化器。同样，我不可能去写十几个优化器。我只是在写一门语言，如果我想成为比如 DEC 计算机的优化器专家，我有相应的背景和训练，但我不想做那个。我首先想构建一个分布式系统，后来当我的朋友和同事开始使用 C 的类特性时，我想帮助他们。他们在做网络模拟、硬件布局、卫星定位等等各种有趣的事情。那是值得做的工作。</p>
<p>所以我意识到，所有这些优化器和代码生成器实际上都有一个通用的接口，它叫 C 语言。所以，让我们把 C 语言当成汇编器来用吧。</p>
<p>事实证明这非常有效。C 语言在底层方面非常出色，这也是我当初选择它的部分原因。所以我用它来处理底层。我本来可以把 C 隐藏起来，重新创建一个可能更好的接口。但我决定保留与 C 的兼容性。</p>
<p>当时我原话是这样说的：“现在我们可以拥有 Dennis 犯过的错误（我们已经了解了），再加上我犯的错误（我们还不知道）。我们还是接受 Dennis 的错误吧，那样更可控、更易于理解。而且我也不用去教人们怎么写 <code>for</code> 循环之类的事情。”</p>
<p>所以与 C 语言的兼容性就是这样来的，部分是作为一种实现策略，部分是为了融入现有的文化和工具生态。</p>
<p><strong>Ryan Peterman</strong>：我在研究中看到，C++ 被用来编写语言工具链的一部分。对我来说，这立刻让人联想到鸡生蛋蛋生鸡的问题——你如何用这门语言来构建正在使用它自身的工具？这是怎么运作的？</p>
<p><strong>Bjarne Stroustrup</strong>：这就是自举（bootstrapping），这并不是什么不寻常的事情。</p>
<p>我是从 C 语言开始的。在 C 中，我写了一个预处理器（pre-processor），它实现了后来 C++ 中“类”的一些基本功能，还有简单的继承和重载等。接着，用那个预处理器，我写了一个简单的编译器，同样是针对 C++ 的一个子集。</p>
<p>现在，我就可以使用运算符重载、一般的重载和类了。所以我可以构建一个处理名称查找等事务的 <code>scope</code> 类。然后你从那里继续前进，用前一个版本去编写下一个版本。你不断推进，几年后，你就拥有了后来被世人所熟知的 C++。我为此写了一本书，编译器也推向了世界。</p>
<p>但我并没有发明这种技术。这被称为“自举”。我想我在本科时就学过可以这样做。</p>
<p><strong>Ryan Peterman</strong>：大多数人看着 C++，会认为那是一门面向对象（object-oriented）的语言。但我多次听你说情况并非如此，或者这并不是你最初的想法。为什么？</p>
<p><strong>Bjarne Stroustrup</strong>：对，我从未称其为“面向对象”编程语言。如果你看《C++ 编程语言》第一版的原文，我最接近的说法是：“有些将这些技术称为基于对象（object-based）”。实际上，它更侧重于类（class），是面向类型的（type-oriented）、面向类的（class-oriented）。</p>
<p>它确实非常完美地支持面向对象的编程技术，尤其是它遵循了 Simula 的模型——定义类型、定义类以及定义类层次结构来处理一组相关的类。但这绝不是它的全部。</p>
<p>例如，我不需要面向对象的复数。我不想通过写 <code>2.add(z)</code> 来操作数字的某些部分。我只想要 <code>2 + z</code>，并且希望它的结果与 <code>z + 2</code> 差不多。不需要点号，不需要箭头。数学在过去的 300 年里发展出了一套完美的符号体系，我想笛卡尔大概是最早使用这套符号的人之一，它非常好用。所以，我不想让所有的东西都是面向对象的。</p>
<p>此外，我希望那些不需要继承、不需要运行时解析（动态绑定）的东西，就不应该使用它们。出于兼容性的考虑，在算术运算和复数等领域我也想要这种效率。</p>
<p>当时我非常热衷于代码的复用（reuse），但我的看法和很多研究人员略有不同。很多研究人员想构建一个允许代码复用的全新语言系统。而我想要复用的是“已经存在”的东西。</p>
<p>Fortran 在那里，带着很多伟大的软件；C 在那里，带着很多伟大的系统软件，甚至在编译器等方面提供了帮助；汇编语言也依然被广泛使用。我想复用那些成果。为了确保这一点能行得通，我不能偏离底层硬件太远。</p>
<p>我不能把所有被认为是理想的东西都建构进去，甚至连我认为理想的东西也不能全做。这就是现实世界。这是你正在攻克的实际问题集。所以你必须尊重你所做工作的约束条件。</p>
<p><strong>Ryan Peterman</strong>：在你编写 C++ 的时候，C 语言已经存在了，而且它的类型系统比 C++ 最终确立的类型系统要弱。我想听听你对这背后权衡的看法，为什么你选择在 C++ 中增强类型系统？</p>
<p><strong>Bjarne Stroustrup</strong>：因为我们需要它。</p>
<p>类型系统中的弱点是最明显的错误来源之一，也绝对是导致无休止测试和调试的原因之一。我讨厌调试。我宁愿把时间花在设计上。你不可能两者兼得。有些人声称他们可以，但其实不行。</p>
<p>所以我想把重心移向“更多的设计”，这有助于减少调试，减少在运行时犯的错误。类型系统就是其中的重要一环。实际上，你们今天在 C 语言中用到的类型系统，也在很大程度上——甚至可以说是绝大部分——比当年要强得多，部分原因正是受到了 C++ 的影响。</p>
<p>此外，如果没有强大的类型系统，有些事情你是无法表达的。我刚才提到了重载。重载对于泛型编程来说是必不可少的。如果你想编写一个 <code>vector&#x3C;T></code>（T 是一个参数类型），你必须有重载，因为你只能在 T 支持你需要的所有接口的前提下对它进行操作。你需要类型系统来解析这些东西，并且这些解析可以在编译期完成。这样编译器可能会变得更复杂，编译速度变慢，但你不需要做那么多调试工作了。</p>
<p>当时在芝加哥的贝尔实验室做过一个大规模的实验。他们有一些团队转而使用 C++，他们想知道生产力是提高了还是降低了。有些人声称编译速度慢拖慢了他们的进度。于是有人测量了切换到 C++ 前后他们究竟耗费了多少编译时间（计算能力）。结果发现，消耗的计算力大致相同。也就是说，C++ 的编译速度大约慢了一倍（在当时），但 C 语言程序员编译的频率是 C++ 程序员的两倍。</p>
<p>这只是一个实验，“慢一倍”只是这一个实验的数据。但我当时就是想推动大家更多地利用编译期的解析。我至今仍坚持这样做。</p>
<p><strong>Ryan Peterman</strong>：对于每种语言，都有静态类型与动态类型的二分法，而 C++ 是最著名的静态类型语言之一。你为什么选择静态类型语言？</p>
<p><strong>Bjarne Stroustrup</strong>：因为我想解决的问题决定的。在像 Smalltalk 这样的语言中，遇到运行时错误你会怎么做？你会进入调试器。如果当时恰好有一个程序员坐在屏幕前处理这个错误，这非常合理。但如果一台电话交换机遇到了运行时错误，你去挂起调试，那是毫无意义的。</p>
<p>此外，你需要性能，你需要让小规模的程序能适应有限的内存。这在今天仍然是真理，因为我想大概 99% 的计算机都是嵌入式系统，它们往往受到内存的限制。如果你进行运行时类型解析，你需要有足够的信息、足够的数据来支持它。而我想把程序塞进小内存里，当时所谓的小意味着 120K、250K、1MB 等等。</p>
<p>我认为这对于很多系统今天依然适用。你可以制造一个几 MB 内存的摄像头。但如果你放入过多的内存，它的体积会变大，成本会上升，电池耗电也会更快。所以我们不会那么做。手机、相机等设备依然受限于内存。</p>
<p>专门针对内存占用优化的静态类型语言在这方面就是表现得更好，这就是我们使用它的原因。我们现在录播客就在用它，我怀疑我们的麦克风里也有芯片，那个领域里有大量的 C++ 代码。这些地方通常是 C 和汇编的组合。</p>
<p><strong>Ryan Peterman</strong>：你提到了在编译时间方面的研究。如果你能更早捕获错误，你编译的次数就会减少，虽然单次编译时间可能更长。我可以看出这里有一个相似的类比：如果使用静态类型语言，你会在更早的阶段捕获错误，因为在你最终构建完成之前，编译器就会冲你大喊大叫。而在动态类型语言中，错误可能会在运行时才出现。如果比较对开发者时间的利用效率，哪种更高？</p>
<p><strong>Bjarne Stroustrup</strong>：我不知道在这方面有没有确凿的研究。但你可以观察一下现状。JavaScript 和 Python 非常受欢迎，它们是运行时检查的，运行速度要慢得多。我的意思是，原生的 Python 运行速度大概比原生的 C++ 慢 70 倍。它之所以能行得通，是因为很多关键的 Python 库是用 C 或 C++ 写的，以此来获取性能。</p>
<p>这就回到了我一开始提出的观点：你需要高级的表达能力，同时也需要能直接操作硬件的东西。在这里他们使用了两种语言组合，但满足的根本需求是一样的。</p>
<p>在动态检查语言中尝试新东西确实更容易，因为你不需要了解太多关于这门语言本身的底层细节。你不需要懂类型系统。而普通的 Web 开发者或天体物理学家并不是计算机科学家，也不想成为计算机科学家。所以它确实有优势。</p>
<p>但问题是，在静态类型语言中由类型系统在编译期发现的错误，在动态语言中会被推迟到运行时才发现。随着系统规模的增长，性能问题开始凸显。而且，你会发现编写高可靠性的软件变得更加困难。例如，在动态语言中，你需要进行多得多的单元测试，因为编译器不帮你做检查。如果你想保证系统绝对不出错，比如电话交换机不能死机，你的汽车不能死机，你的飞机不能死机。你需要的是保障（guarantees），而这些在极其灵活的动态类型系统中是很难提供的。</p>
<p><strong>Ryan Peterman</strong>：我觉得 C++ 臭名昭著的一点是它的内存安全问题，或者说里面存在的各种“自爆开关（footguns）”。</p>
<p><strong>Bjarne Stroustrup</strong>：我对这个话题真的感到厌烦了。我已经很多年没有遇到过这些问题了。</p>
<p>有人做过一项关于明显的缓冲区溢出（buffer overflows）以及利用这些漏洞进行黑客攻击的研究。结果发现，绝大多数这些案例都发生在人们编写 C 风格代码，或者直接写 C 语言的时候。Herb Sutter 有一个讲座展示了实际数据，非常具有说服力：这类问题中，超过 90% 都是因为没有使用现代 C++ 的编程方式。</p>
<p>他们使用原始指针（raw pointers）来传递数据，却不附带元素数量信息。没有胖指针，没有 <code>span</code>。但你在 C++ 中明明是有这些东西的。你可以使用它们。你可以使用 <code>vector</code>。我们有强化过的标准库（hardened libraries）。每个人都有在运行时做检查的强化库，苹果有，谷歌有，微软也有。只是直到现在它们还没有成为强制的官方标准。C++26 提供了一个标准化的强化选项。而我正在从事的关于 Profiles 的工作，将为你提供一种机制，以保证你不会再做那些蠢事。</p>
<p>所以，无论从基础上还是理论上，这个问题在很多年前就已经被解决了。人们只是习惯性地做他们一直做的事情，然后遇到他们一直遇到的问题。这让我感到很难过，这也是促使我致力于制定编码指南、强制性 Profiles 策略以及教育工作的原因之一。教育是解决这个问题的途径之一。</p>
<p><strong>Ryan Peterman</strong>：有没有办法让编译器直接阻止人们做所有那些高风险的事情？现代 C++ 默认开启这些限制了吗？</p>
<p><strong>Bjarne Stroustrup</strong>：默认还没有，但应该这样。我正在为 C++29 提案这一功能。其实更简单的版本本应该在 C++26 中就加入，但在 C++ 标准委员会里，依然有很多人非常执着于他们的旧代码和旧的做事方式。有人说，标准化的内容应该仅仅是工业界已经普遍采用的做法。但如果工业界普遍存在的是 Bug，你就应该采取不同的应对策略。</p>
<p><strong>Ryan Peterman</strong>：标准委员会这个话题我很想聊聊。这很有趣，这门语言现在是由“民主”决定的。我想问的是，如果这是一个独裁政体，也就是你拥有绝对的话语权，哪些语言特性会被加入进来？可能更难通过的是哪些？</p>
<p><strong>Bjarne Stroustrup</strong>：首先，这从来不是一个独裁政体，我从来没有拥有过绝对的控制权。我认为，一旦你有了用户，你就承担了确保他们得到帮助、确保他们的代码能正常运行的责任。你不能不停地破坏语言本身。那就是学术界开发语言的方式——他们为了改进可以随时推翻重来，所以他们无法维持一个稳定的用户群体。</p>
<p>我并不是主动选择成立标准委员会的。我是选择了对社区负责。但有一天，代表 IBM 和惠普（HP）的两个人走进了我的办公室。我记不清第三家是 Sun 还是 DEC 了。总之，当时世界上最大的计算机和软件供应商的代表来到了我办公室。那是 1989 年。</p>
<p>他们说：“Bjarne，你想帮我们在 ISO 的规则下标准化 C++ 吗？”我说：“不，我不能那么做。我还在做实验，它还不完整。”</p>
<p>他们说：“不，Bjarne，你不明白。我们的组织不能使用一门没有被标准化的语言。我们不能使用一门被我们可能与之竞争的公司（即 AT&#x26;T）所拥有的语言。我们当然信任你，但我们不信任你的雇主。我们有时是竞争对手。而且你可能会被你的老板干预否决。不，不，不。我们需要一个标准，我们需要一个标准委员会。”</p>
<p>这段对话持续了大约一个小时，他们一直在向我施压。痛，太痛了。（笑）最后我说：“好吧，我会按照你们的建议在 ANSI 规则下标准化 C++。计算机社区需要这个。顺便问一下，ANSI 标准化的规则到底是什么？”</p>
<p>他们告诉了我，我们在一年后启动了。但这就是它发生的原因。一些非常重要的组织要求这种标准化。</p>
<p>C 语言当时正走在标准化的轨道上，而 AT&#x26;T 作为一个主要使用软件的公司，我发现他们也支持标准化。所以我编写的文档就成了它的基础。实际上，我重写了成为 ARM（《带注释的 C++ 参考手册》）的文档。那本书给出了语言的定义和手册，以及每个特性的原理说明和实现方式。那成为了标准化的基础文档。</p>
<p><strong>Ryan Peterman</strong>：当他们对你施压时，如果你当时直接拒绝会发生什么？</p>
<p><strong>Bjarne Stroustrup</strong>：我想，C++ 最终可能会褪色成一种只被少数人喜爱的可爱的“学术语言”，并从计算领域的主流中彻底消失。</p>
<p>有些人说得比我更绝对。他们说 C++ 能够广泛传播并被大量使用，就是因为它有一个公共的标准。它不属于任何一家公司。这有时也是阻挡那些想要“杀死 C++”的竞争者的一道屏障。</p>
<p>我记得当年 Java 的广告，有人站出来说，我们在两年内就会彻底杀死 C++。我觉得这很不礼貌。但不管怎样，今天我们拥有的 C++ 开发者数量，是他们说那番话时的 10 到 12 倍。所以，他们并没有得逞。</p>
<p><strong>Ryan Peterman</strong>：为什么 C++（我不说是战争，从普及度来看）最终获得了比 Java 更广泛的应用？因为 Java 背后有大公司的支持，投入了大量的营销资金，而 C++，我想你说过它用于营销的预算几乎是零。</p>
<p><strong>Bjarne Stroustrup</strong>：接近零，也就是三年一共 5000 美元而已。而 Sun 公司用于推广和营销 Java 的资金，比投入在 C++ 开发上的资金总和还要多得多。</p>
<p>直到今天，标准委员会仍然面临一个问题：作为非营利组织，没有资金支持。这意味着很难进行实验，很难部署新东西。而且其他语言社区还在不断挖走 C++ 编译器和工具的开发者，因为他们很优秀。这使得我们很难预测实现新特性的速度。</p>
<p>我上次查看时，C++ 标准委员会有 527 名成员。我们依赖共识（consensus）来运作。因为如果你没有共识，你就会产生“方言（dialects）”（即分裂出不同的语言版本）。我们不希望一个特性的投票结果是 60 对 40，更糟的是 52 对 48 就通过。我们绝对不这样做。这确实痛苦、乏味，但也很好。</p>
<p><strong>Ryan Peterman</strong>：当你说共识时，是说需要 100% 同意吗？</p>
<p><strong>Bjarne Stroustrup</strong>：100% 并不是必需的。我们不需要全体一致同意（unanimity）。我们需要的是压倒性的多数（massive majority），基本上我希望能看到 90% 的支持率。如果我们只拿到 80% 的支持，我就会开始担心了。</p>
<p><strong>Ryan Peterman</strong>：规则里有没有明确写下限是多少？</p>
<p><strong>Bjarne Stroustrup</strong>：规则里没有硬编码下限。规则是：由 ISO 委员会的召集人（convenor）来决定什么是“共识”。所以仅仅靠单纯的数字是不能说明问题的。</p>
<p>你能想象一个投票结果是 95% 对 5% 的情况吗？但是，如果这 5% 代表的是来自谷歌、苹果、微软以及其他大厂的 C++ 编译器和标准库的实现者呢？你能说这达成了共识吗？我可以向你保证，没有哪个召集人会把这称为“共识”。</p>
<p><strong>Ryan Peterman</strong>：这直觉上很合理。但我有时也会想，民主决策是否需要一些客观规则。如果召集人做出了错误的决定怎么办？</p>
<p><strong>Bjarne Stroustrup</strong>：确实发生过。但你不能只依赖数字规则。并不是每个人都关心语言的整体。也不是每个人都完全理解正在发生的事情。你参加第三次会议就有投票权了。所以你可能会遇到一个有投票权的人，但他只有 8 个月的标准化经验，不了解标准化的全貌，只知道他自己所在小开发团队里遇到的情况。</p>
<p>你需要一定程度的判断力，并且你希望召集人具备这种判断力。</p>
<p>达成共识的另一种反面情况是，你有一个看似压倒性的数字共识，但有 10 个国家的代表不同意，那也不是共识。</p>
<p>如果看起来没有问题，绝大多数人都赞成，那就没问题。但如果存在分歧，召集人会询问各国代表团的负责人，询问各家实现者，即那些对于将新特性投入实际使用至关重要的核心人物。在做出决定之前，有时也会咨询教育工作者。</p>
<p>一旦发生分歧，并不是每个人的权重都是相等的。</p>
<p><em>(Ryan Peterman 插入了一段 Cursor 3 和 WorkOS 的赞助广告词，讲述了他在为播客制作文本时使用 AI 代理修复文字拼写错误，以及使用 WorkOS API 为 SaaS 产品添加 SSO 登录功能的体验，此处略去翻译不影响主体访谈内容)</em></p>
<p><strong>Ryan Peterman</strong>：关于标准委员会，我在你的一些文章中看到，你说过你提出过的收到负面反馈最多的想法之一是 <code>auto</code>。我知道 <code>auto</code> 最终还是被加入了，但为什么当时它会受到如此强烈的反对呢？</p>
<p><strong>Bjarne Stroustrup</strong>：因为它在当时显得太不寻常了。人们认为它在削弱类型系统。而且，它为相当通用的、不严重依赖语法的泛型编程打开了大门。<code>auto</code> 实际上是后来概念（Concepts，用于约束泛型代码）的起点。<code>auto</code> 就是最简单的约束——它必须是一个类型，而不是一个值（比如数字 7）。</p>
<p>也许当时我没有解释清楚。而且委员会里成员的背景各不相同，也许他们不了解像 ML 或 Haskell 这样支持泛型推导的语言。</p>
<p>所以当时情况很糟糕。但不管怎样，我们最终还是让它通过了，因为我们确实需要这样的东西。但这还不够。我后来检查了一些工业软件，发现了滥用 <code>auto</code> 的问题。</p>
<p>你只应该在你对此处需要的类型有明确概念时才使用 <code>auto</code>。它在泛型代码中很好用，你编写代码，最后系统会检查推导出的类型是否正确，<code>auto</code> 是否解析为支持你将要执行的操作的类型。这就是后来 Concept 机制正式化的内容。</p>
<p>但我注意到有一群人过度使用了 <code>auto</code>，实际上是在一个网络框架中。他们反馈说开发速度被拖慢了，虽然不是因为 Bug，而是因为他们不得不去查找被调用的函数，以弄清楚那个 <code>auto</code> 到底绑定了什么类型。然后他们不得不加上注释来说明这个 <code>auto</code> 究竟代表什么。</p>
<p>所以你会看到写着 <code>auto c = ...</code>，然后后面跟着一句注释：“这里必须是一个输入通道（input channel）”。既然这样，你完全可以直接定义 <code>InputChannel</code> 类型，然后写 <code>InputChannel c = ...</code>，这样就很清楚了。我最初的设计其实就是说 <code>auto</code> 是最简单的概念，你本就应该写明具体概念。但当时委员会想要一个明确的指示符，表明这里正在进行类型推导。</p>
<p><strong>Ryan Peterman</strong>：我还看到了另一个关于标准委员会讨论偶尔会很激烈的轶事。你提到过一种“穿梭外交（shuttle diplomacy）”，在房间的两个角落之间来回跑，因为我记得当时是 IBM 和 Intel 对内存模型有不同的支持需求？</p>
<p><strong>Bjarne Stroustrup</strong>：是的，没错。这背后的故事很有意思。其实上周我还在和当时的 IBM 代表 Brian MacKay 聊天，我们讨论了当年发生的一些事情。所以这事还被人记着呢。</p>
<p>基本上，IBM 当时在做 PowerPC 架构，而 Intel 在做 X86 架构。它们底层硬件的模型截然不同，尤其是在与缓存（caches）协作的方式上。</p>
<p>当时代表 Intel 发言的其实不是 Intel 本公司的员工，也是个很棒的人。我经常在我的演示中使用他做的一些幻灯片。所以我认识这些人，但他们当时完全陷入了僵局。要知道，这些都是极其庞大的组织，外面跑着海量的代码。</p>
<p>IBM 的代表 Brian 说，他们有大量的软件，尤其是最底层的甚至微代码级别的软件，都依赖于他们现有的模型方式。而且当初写这些代码的人早就离开公司了，那都是很久以前写的。即使 Intel 的方案是对的，他们也根本不可能重写所有这些代码并保证不出错。</p>
<p>而 Intel 那边也有类似的论据和观点：“我们的更好，我们正在使用它。”</p>
<p>所以我当时在干嘛呢？他们真的分坐在一个大房间的对角线两个角落。于是我走到 Intel 的代表那里，问：“这里的问题到底是什么？给我解释一下。”我听完，理解了，然后走到 IBM 那边说：“他是这么说的。”他们回答：“嗯，但是还有这个、这个和这个。”然后我又走回去。</p>
<p>我花了几个小时，真的是在搞“穿梭外交”，从房间的一个角落走到另一个角落。最终，我们达成了协议，这就是后来的 C++11 内存模型。几年后，他们双方都承认，他们现在使用的是自己原有方案和对方引入方案的结合体。所以实际上，最终的结果是一次成功的交叉授粉和技术改进。</p>
<p><strong>Ryan Peterman</strong>：为什么必须要你来做穿梭外交？为什么不能大家聚在一起开个会讨论？</p>
<p><strong>Bjarne Stroustrup</strong>：因为他们已经试了好几天了，甚至可能在之前的会议里也试过了，但是没用。我想我当时扮演的角色只是在做翻译和提问。他们都是那个级别绝对的专家。我并不认为自己在那个极深层次上是个专家。虽然我也做过硬件，写过微代码，我不是外行，但这群人是真的厉害。</p>
<p>那位 IBM 的代表，现在是 Linux 内核底层同步机制的核心人物。我们今天仍在大量使用他的成果。他有一个 C 语言版本的实现，这样就可以放进 Linux 内核里。</p>
<p><strong>Ryan Peterman</strong>：当阅读你在这些论文中的写作时，似乎在 1995 年，你有一个在 C++ 中引入某种形式的自动垃圾回收（garbage collection）的想法。这让我很惊讶，因为当我想到 C++ 时，我最直接的反应之一就是“没有垃圾回收器”。我们都要手动管理内存。这到底是怎么回事？</p>
<p><strong>Bjarne Stroustrup</strong>：这里有两件事。首先，我一直想要“自动化资源管理”，而不仅仅是“垃圾”和“内存”。为了实现这一点，我们有了构造函数、析构函数，以及后来被称为 RAII（资源获取即初始化）的技术——这可能是我起过的最糟糕的名字。但我当时实在太忙了。</p>
<p>但在标准委员会里，有一批人坚持认为我们需要能够进行垃圾回收，而且当时市面上也有现成的垃圾回收器。其中代表人物是 Hans Boehm，他代表了基于内部模型的方向。他写的一个保守型垃圾回收器至今仍在使用。我们当时认为我们需要一个接口，以标准化在 C++ 中如何使用这种垃圾回收器。</p>
<p>所以我其实是在倾听那些专家用户的意见，他们认为这是必要的。而我个人始终认为对内存管理和资源管理提供自动化支持才是最重要的。从一开始我就这么认为。我不觉得垃圾回收适合我当时从事的大部分工作，但毫无疑问，自动化的内存管理是理想的目标。</p>
<p>经过漫长的一系列讨论，我们找到了一个大家都能同意的接口，并将其放入了 C++11 中。但我们在接下来的 10 年里发现，垃圾回收的使用量在减少。这是因为 RAII（一直都在那里的资源管理机制）变得越来越好，被理解得越来越深，使用也越来越广泛。</p>
<p>此外，那些仍然使用垃圾回收器的人，并没有使用那个官方的标准接口，因为他们找到了做得更好的方法。所以今天，仍然有少数人在做垃圾回收，但它已经不再是标准的一部分了。</p>
<p><strong>Ryan Peterman</strong>：这在技术上是怎么运作的？它像是在内存分配方法外面包了一层封装（wrapper）吗？</p>
<p><strong>Bjarne Stroustrup</strong>：是的。你提供了一个不同的底层实现，比如替换掉 <code>new</code>、<code>malloc</code> 或 <code>operator new</code>，然后 <code>delete</code> 的语义也会发生相应的微小改变。</p>
<p><strong>Ryan Peterman</strong>：在 C++ 社区有一个关于瓦萨号（Vasa）战舰的警示故事。我很好奇为什么这个故事这么出名？</p>
<p><strong>Bjarne Stroustrup</strong>：有一次我们在斯德哥尔摩开会。如果你有机会去斯德哥尔摩，一定要去看看那艘华丽的沉船——瓦萨号。那是一艘 1600 年代的战舰。这背后有个故事，我经常讲给别人听。</p>
<p>瑞典国王下令建造一艘战舰，要求它必须是当时最好、最壮丽的战舰。它不仅要是一艘强大的战斗舰，还要用于外交巡访，所以必须极其华丽。他们铺设了龙骨，开始建造。</p>
<p>但后来，他们听说一个潜在的对手正在建造拥有两层火炮甲板的战舰。而这艘船原本被设计成只有一层火炮甲板的旧式战舰。如果你把一艘单层火炮甲板的战舰放在双层火炮甲板的战舰旁边，结果是显而易见的：单层甲板战舰会被打成筛子，然后沉没。</p>
<p>于是，国王下令这艘船现在必须拥有两层火炮甲板。可他们已经开始建造了。所以他们硬生生增加了一层甲板，并在上面放满了大炮。而且国王想要船造得更大，想要更多的雕像和华丽的装饰。所以这艘船变得有些头重脚轻了。</p>
<p>有传言说——我没核实过，所以可能是错的——这艘船的设计师因为感到恐惧而自杀了。但我相信另一个事实不是传言：在船建成后，他们进行了稳定性测试。当时测试战舰稳定性的方法是，让全体船员从船的一侧跑到另一侧，来回跑，以此引发谐振摇晃。如果船能承受 14 次这样的来回跑动，就说明它能经受住波罗的海和北海的风浪。</p>
<p>据记载（我认为这是事实），他们只跑了 7 次就停下来了，因为船体看起来太危险了。</p>
<p>那大概是在 1628 年。战舰完工了，这是你见过的最华丽的船。它在斯德哥尔摩港口起航。喇叭齐鸣，彩旗飘扬，船员的家属也在船上，场面极其盛大。</p>
<p>它刚刚驶过海港的一半，一阵阵风吹来，船只发生倾斜，就这么沉没了。它沉入了一个氧气含量极低的海底区域，所以保存得非常完好，后来被打捞了上来。你现在可以去参观它。</p>
<p>所以我把这个故事讲给标准委员会听。我指出他们做错了一件事：他们在一个没有得到改进的基础上，硬生生堆砌了更多的新特性。永远要优先改进地基，确保它不仅仅是随意添加的特性集合，因为那会带来不可控的复杂性。此外，绝对不要在你的测试环节上妥协。那极其危险。</p>
<p>更重要的是，你们肯定遇到过高层老板下令要做某事的情况。但高层并不总是知道什么是对的。有时，专业的做法是说：“不，我们不这样做。我们必须稳扎稳打。”如果当初他们说：“好吧，我们先建一艘单层甲板战舰，只是不叫它瓦萨号。明年再从头设计建造一艘真正的双层甲板战舰。”那就不会有任何问题。</p>
<p>但高层管理人员——那位当时身在波兰、甚至没亲眼见过这艘船的国王说：“不行，必须按时交付。”所以他们按时交付了一个根本无法胜任任务的东西。但那艘船真的很漂亮，值得一看。</p>
<p><strong>Ryan Peterman</strong>：在某个时候，有人证明了 C++ 的模板实例化机制是“图灵完备”的。这意味着编译器在预处理 C++ 程序时所做的工作，实际上可以用于执行任意计算。我只是想搞清楚这怎么可能？有人甚至在编译期计算了素数。这是怎么运作的？</p>
<p><strong>Bjarne Stroustrup</strong>：算素数那个只是为了满足好奇心，它利用报错信息输出了结果。但要让一个系统图灵完备，你需要某种形式的“迭代”或“递归”，还需要一个“条件判断”。有了这些，你就能实现图灵完备了。</p>
<p>当时至少有一些理论家说：“我们不能允许这样做，这会导致编译器陷入死循环永远运行下去。”发现这种玩法的第一人甚至也认为我应该禁止这种行为。</p>
<p>但我的反应是：“这看起来很有用啊，太棒了。”而且我认为我是对的。此外，没有任何东西会“永远”运行下去。如果你有一台真正的图灵机，你需要一条无限长的纸带。在现实中，你需要雇一支海军不停地在后面铺设纸带。我们显然不会那么做。</p>
<p>关键在于，在陷入真正的死循环之前，编译器就会耗尽资源崩溃掉。机器的资源是有限的。所以除非代码有 bug，否则这在实际中不会成为问题；如果有 bug，它也绝对会被捕获（比如编译超时或内存耗尽）。所以不是问题。</p>
<p>后来发生的事情是，人们开始滥用模板来进行简单的计算，比如算素数、算阶乘之类的。语法看起来极其糟糕，而且非常昂贵，消耗了大量的内存，这就变成了一个实际问题。</p>
<p>这就是为什么后来我和 Gaby Dos Reis 引入了 <code>constexpr</code> 的原因。这基本上意味着你可以让完全普通、可读的代码在编译期执行计算，这不仅简单得多、符合我们的日常习惯，而且编译速度快得多，生成的代码通常也更快。现在我们有了这个特性，如果你想保证某个计算必须在编译期完成，你可以使用 <code>consteval</code>。</p>
<p>这彻底解决了那些通过图灵完备模板机制来做复杂计算的滥用现象，把它们变成了普通的函数调用。</p>
<p><strong>Ryan Peterman</strong>：一般来说，对于编程语言有一种直觉：你离机器底层越近，性能就越高。我倾向于认为 C 语言比 C++ 离机器更近，或者说执行效率更高。</p>
<p><strong>Bjarne Stroustrup</strong>：不，并不是这样。C 语言没有 C++ 那样强大的编译期计算能力。不管怎样，这两种语言底层的机器模型是完全一样的。实际上 C 语言借用了 C++11 的内存模型。所以如果你用两种语言编写相同的逻辑代码，你会得到相同的执行结果，区别在于 C++ 编译器能在编译期做更多的事情。</p>
<p>因此，在大多数情况下，C++ 运行得和 C 一样快，甚至更快。如果你给优化器提供更多的类型信息，它就能做得更好。</p>
<p><strong>Ryan Peterman</strong>：我之前想问的正是这个：你说过 C++ 可以比 C 性能更高，但我倾向于认为，更多的“抽象”会带来一定的性能成本。</p>
<p><strong>Bjarne Stroustrup</strong>：但那些抽象在编译时被消除（优化的）了。这就是为什么我总谈论“零成本抽象（zero-overhead abstraction）”。但现在开始有人挑我毛病了，因为这个词其实低估了 C++ 编译器的能力。我们现在完全可以做到“负成本抽象（negative overhead abstraction）”。</p>
<p><strong>Ryan Peterman</strong>：如果我极其擅长写汇编，而且我有无限的时间来写，那性能比较起来会怎样？</p>
<p><strong>Bjarne Stroustrup</strong>：如果你极其聪明，并且拥有无限的时间，你可以做得更好。但在绝大多数情况下，我们不再比优化器聪明了，而且我们也没有无限的时间。</p>
<p>如果我们足够聪明，我们也只能在极小的一段代码上展现我们的聪明才智。现在的问题是，我们有没有足够的时间来发挥这种聪明？</p>
<p>这甚至开始影响所谓的“巧妙代码（clever code）”。去年我在纽约给一群对性能有极致要求的金融界资深开发者做了一场题为“不要试图太聪明（Don't be clever）”的讲座。其实原标题是“不要太自作聪明（Don't be (too) clever）”，只是我发不出括号的音。（笑）最后我算是全身而退了。</p>
<p>我的核心观点是，C++ 提供的常规设施对你 98% 以上的代码来说已经足够好了。如果你想省出时间去钻研那一点极其底层的巧妙优化，你就应该在剩下 98% 的地方使用现代高级的 C++ 技术，这样你才有时间去做底层优化。</p>
<p>今天“巧妙的优化”面临的问题是，它们往往是高度依赖具体机器架构的。也就是说，如果你换了一台新电脑，或者升级了编译器版本，你当初极其巧妙的优化代码可能反而会导致性能下降（pessimized）。从 80 年代以来，我反复看到这种情况发生。</p>
<p>总有一群人除了在下一代硬件上尝试各种极端的优化手法外什么也不做。我提升代码性能的标准手段实际上是：首先把那些“自作聪明”的底层 Hack 删掉，然后看看代码是跑得更快了还是更慢了。</p>
<p>通常它会跑得更快。因为那些“聪明”的技巧，至少是 90 年代风格的聪明技巧（今天仍然有很多，因为这些技术留在了人们的脑子里，并且一些旧代码依然留存），往往使用了一堆乱如鸟巢的指针，这会给现代的编译器和优化器带来极大的麻烦。</p>
<p>他们有时还会使用更多的内存分配，这也是不可取的。你想要最小化内存访问次数，最大化缓存命中率等等。现代编译器在这方面变得非常非常出色。</p>
<p>我看到过很多这种现象。我和我的一位在西班牙做流体动力学研究的朋友一起写过一篇论文。我们把一个真实的性能测试用例代码里所有“巧妙”的优化全都删掉了。通过把代码量缩减到原来的 80%，我们“仅仅”获得了 20% 的性能提升。有些人认为这不显著。但我认为这是一个证明该理念行之有效的显著证据。你只应该在真正需要的时候才应用底层优化。</p>
<p>高德纳（Donald Knuth）说过“不要过早优化（premature optimization）”，他还指出有大约 2% 到 3% 的代码是你真正应该去优化的，这与我引用的数字完全一致。所以，先使用高级抽象设施来构建东西，看看是否足够快；如果不够快——而且你必须进行实际的计时测量，不能靠猜——你再找出时间耗费在哪里，然后针对那一点进行优化。但在很多时候，你根本不需要走到那一步，因为它已经足够快了。</p>
<p><strong>Ryan Peterman</strong>：我明白了。所以当你在这里说到“巧妙（cleverness）”时，指的是人类手动的、为了压榨性能而做的底层内存或结构管理？你其实是说，如果你不去做这些，你可以给编译器留出更多的优化空间，它能做得非常好。</p>
<p><strong>Bjarne Stroustrup</strong>：是的，现代编译器的优化能力比过去强太多了。那些在 1990 年代被认为是极其巧妙且优化得当的代码，在今天往往反而成为性能瓶颈，因为机器架构变了，编译器的能力也极大提升了。</p>
<p><strong>Ryan Peterman</strong>：当我审视今天的行业时，越来越多的代码正在由机器而不是人类编写。我觉得以往很多编程语言的设计都在思考如何使其更适合“人类”解决问题和编写代码。我很好奇，如果你认为未来越来越多的代码由大语言模型（LLM）等机器编写，你觉得编程语言的设计会发生改变吗？</p>
<p><strong>Bjarne Stroustrup</strong>：我认为，在我最感兴趣的那个领域（指高性能、系统级、对安全性要求极高的核心系统），代码依然将由人类编写，并且人类会继续使用“抽象”。我所看到的人工智能在这一领域尝试生成代码的例子，并没有取得成功。</p>
<p>它们会生成更多的 bug，带来更多的安全漏洞。它们生成的代码非常臃肿，这又回到了刚才说的性能退化问题，因为你使用了更多的内存。而且，这些 AI 生成的代码很难被验证。</p>
<p>能够验证这些代码的资深开发者——我已经看到其中一些人开始选择退休了，因为他们根本不想把精力耗在去验证那种“你稍微改一下提示词（prompt），出来的一大坨代码就全变了”的产物上。</p>
<p>此外，我关心的很多事情都涉及到监管机构和严格的验证流程。当你做出一项修改时，你必须能够确切地验证你到底改了什么。但如果使用 AI 工具，哪怕你只是修改了一个很细微的提示词，生成的所有代码可能都会发生翻天覆地的变化。你现在必须重新检查每一行新生成的代码。要知道，AI 生成的代码量通常比人类手写的还要多。</p>
<p>当人类程序员做修改时，那通常是一个局部的改动，你可以针对这个局部改动去寻找其带来的影响。如果 AI 写了代码，你其实并不知道它具体在哪里做了修改。你必须大海捞针般去寻找。如果你做的是以前被做过无数次的事情，比如写一个标准的 Web 应用，你刚才说的可能是对的。</p>
<p>我也不是说 AI 一无是处。那不是我的意思。它可以用来撰写文档——当然同样需要人工审核，但它在处理文本方面很擅长。至少在目前，它并不擅长编写对安全性和性能要求极高的关键代码。</p>
<p>假设世界上 70% 到 80% 的代码不符合这种严格的模式。但我关心的是那剩下的 10% 到 20% 的关键代码。目前 AI 在这个层面上还达不到要求，而且我在基于现有大语言模型（LLM）的路径上也看不到它达标的希望。</p>
<p>此外，LLM 的工作原理是用海量的训练数据进行训练，而这些数据必然是旧代码。我对自己工作的认知是，确保人们编写新东西，并使用能够改进旧代码的新技术。所以我发现基于 LLM 的代码，实际上是在模仿旧代码，重现旧的性能瓶颈，并重复那些旧的 bug。</p>
<p>也许你可以改进这一点。我听到有传闻说现在有专门根据我写的文章和指导原则训练的“Bjarne 应用”。但这同样存在问题，因为我现在的想法也不完全等同于我 20 年前说过的话。但不管怎样，我们走着瞧。</p>
<p>甚至计算机科学先驱 Dijkstra 曾经也探讨过这种可能性。他非常断然地指出，把自然语言作为编程语言的想法是愚蠢的。（他说话可比我不客气多了）。</p>
<p>我认为，像英语这样的语言极其灵活，我们说的话通常具有极大的歧义。而我们需要的是一门极其精确的编程语言，那是工程，是数学，不是英语。</p>
<p><strong>Ryan Peterman</strong>：对于那些性能或安全性至关重要的代码，我想总会有一小部分人尝试使用 LLM 去写。根据你刚才所说，直觉上你会预见它带来更多的崩溃和 bug，因为代码不够严谨，而且那些真正擅长这个领域的高手，往往不愿意把所有的生命都耗在替 AI 检查代码上。</p>
<p><strong>Bjarne Stroustrup</strong>：另一个问题是，公司想要消灭初级程序员，因为这个群体数量庞大。但如果你真的这么做了，你未来的高级程序员从哪里来？</p>
<p>走着瞧吧。你可以在 10 年后再问我同样的问题，那时我们会有更多的知识。毫无疑问，我今天说的一些话在 10 年后可能会被证明是错的，但我猜我今天说的话中也有相当一部分会在 10 年后被证明是对的。</p>
<p>AI 的支持者总是告诉我，要么这个问题已经被解决了，要么它将在“下一个版本”中被解决。但我听说 Anthropic 的 4.7 版本在某些方面比 4.6 版本出了更多问题，原因我不懂。但那种“下一个版本就会解决所有问题”的假设，始终是一个非常危险的想法。</p>
<p>此外，AI 的成本正变得越来越高昂。如果你必须斥资一亿美元建立一个数据中心，并为它支付极其高昂的电费，你需要裁掉多少个初级开发者才能让这笔账算得过来？他们开始面临资金压力了。这并不是毫无问题的。而我所处的子领域，在这方面的挑战可能比大多数领域还要大。</p>
<p><strong>Ryan Peterman</strong>：我在一篇关于你的个人资料中看到，他们问你是如何坚持在 C++ 上深耕这么多年的，是什么在激励着你？你说第一是构建未来的乐趣，第二是确保 C++ 不断向前发展的责任感。当你最初开始做 C++ 时，我无法想象你能预料到这会是一段长达几十年的旅程。</p>
<p><strong>Bjarne Stroustrup</strong>：不是几十年。但我知道那将是一段相当长的旅程，因为我知道我不可能一蹴而就地构建出我理想中的语言。我只能先构建出它的一个子集。</p>
<p>这里有两个原因。首先，我们当时是一个很小的团队，缺乏资源，缺乏时间。其次，我当时并没有足够的输入反馈来确保我设计的每一个细节都是绝对正确的。所以这回到了工程学的问题：先构建你能构建的，看看什么行得通，然后不断改进它。所以我从一开始就知道我是要投入这样一种长期迭代中的。</p>
<p>我知道我正在构建一门“注定要进化”的语言。注定要进化意味着你在做某些决定时是有长远眼光的。例如，这也是 C++ 为什么不单纯是一种面向对象编程语言的原因之一，因为我能看到世界上存在很多似乎不适合那种范式的东西。所以我知道我们会进化。</p>
<p>那个问题的另一半答案，关于是什么让我坚持下去的，是它的实际应用（Applications）。</p>
<p>看到 C++ 被用于各种有趣的领域，真的非常美妙。我去了 NASA 喷气推进实验室（JPL），和那些做火星漫游车的人交谈。那是非常酷的东西。我去过欧洲核子研究中心（CERN）。今年夏天我还要去 CERN 看看他们是如何进行高能物理研究的。我对高能物理一无所知——好吧，可能比普通人多一点点，但离物理学家差远了。</p>
<p>去那里，看到他们在做着极其有趣的事情，有些事会让你大开眼界。几年前我在 CERN 遇到一个人，他的工作是开门和关门。</p>
<p>那些门是用铅做的，重达几吨。它们在轨道上移动来封闭某个区域，以防辐射之类的事情。我不知道具体细节，但关键是：启动这扇门并不难，你有引擎驱动；但你必须确保你能精准地让它停下来。因为当一个重达几吨的庞然大物以一定速度撞向墙壁时，它可不是说停就能停的。你必须编写非常精密的控制代码。</p>
<p>那段代码非常有趣，我从中也学到了东西。我至今仍然到处旅行，和各种人交谈，看看 C++ 正在被用来做什么，它能用来做什么，以及它不能用来做什么。保持学习，学习本身就充满乐趣。</p>
<p><strong>Ryan Peterman</strong>：有几句非常著名的引用自你的话，我想如果你能给它们提供一些背景信息会很有趣。其中一句是：“C 语言让你很容易开枪打中自己的脚。C++ 让这变得难了一些，但一旦你打中，它会把你的整条腿炸飞。”</p>
<p><strong>Bjarne Stroustrup</strong>：哈哈，是的。80 年代我在波士顿做演讲时，有人在台下问了个问题，我当时几乎没经过大脑思考就甩回了这句话。</p>
<p>但这是一句非常棒的引用，而且它是正确的。</p>
<p>曾获得诺贝尔物理学奖的 Arno Penzias（他可不是什么小人物），曾经试图向贝尔实验室的一大群经理们解释 C++。他说：“如果你有一把电动工具，你不能在不知道怎么用的情况下随便乱用。如果你用的是一把普通的手锯，你就像这样锯（做前后拉锯动作）；如果你拿了一把电锯，你还试图用那种前后拉锯的动作去锯，电锯就会猛烈回弹，你必须非常幸运才能不把自己弄伤。”</p>
<p>注意，这和我那句话传达的故事核心是完全一样的。</p>
<p>这背后蕴含的道理是：如果你获得了一个强力的工具却去滥用它，你会招致更大的灾难。一辆加速极快的跑车，能以一种老式慢吞吞的汽车绝对做不到的方式，把你直接裹在树上。这就是拥有强力工具的基本属性。</p>
<p><strong>Ryan Peterman</strong>：你还有另一句很棒的名言：“如果一个人只懂一种编程语言，他就不应该称自己为专业人士。”显然你会推荐大家学习 C++，但如果他们必须去掌握第二门或第三门语言来成为更优秀的工程师，你会推荐什么？</p>
<p><strong>Bjarne Stroustrup</strong>：是的。如果你看过那次采访，你会发现我在这个问题上故意含糊其辞。</p>
<p>关键并不在于你具体懂的是“哪一种”其他语言，而是你从这些语言中汲取到了一种嵌入其中的全新思想体系。所以你应该去做的是，学习一些与你现在使用的语言“截然不同”的语言。我并不是太在意那具体是什么语言。</p>
<p>我想我当时的回答是：在今天，去学一门脚本语言吧，比如 Python 或 JavaScript。然后我想我提到了 Unix Shell 之类的。去看看函数式语言，ML 或 Haskell 都是明显的选择。或者随便挑点不一样的东西。</p>
<p>核心观点是，你绝不能被困在你当前语言所固有的思维模式里。这就好像如果你只会一种人类语言也是不好的，你知道那些懂三种语言的人叫什么吗？三语者。懂两种语言的叫？双语者。那只懂一种语言的叫什么？美国人。（大笑）——这在除了美国之外的地方是个非常受欢迎的笑话。</p>
<p>对于编程语言也是完全一样的道理，但我认为在编程语言领域，这一点更为重要。因为你是在构建真实的世界，你应该用不同的理念和技术来拓宽你的视野。</p>
<p><strong>Ryan Peterman</strong>：另一句话是：“那些自以为无所不知的人，真的非常让那些知道自己一无所知的人感到恼火。”我很好奇这背后的语境。</p>
<p><strong>Bjarne Stroustrup</strong>：这很简单。世界上有太多的人，认为几乎所有事情都有一个极其简单的解决方案。</p>
<p>在我的语境里，他们会跑来告诉我 C++ 其实可以变得多么简单。在某种程度上这是真的——如果你只想做“一件”具体的事情（通常是他们脑子里正在想的那件事），你确实可以设计一种简单得多的语言。他们经常会说：“如果我们把 C++ 的这一部分扔掉，它就会变得简单得多、漂亮得多。”通常他们想扔掉的是对 C 语言的底层兼容部分。</p>
<p>但如果你真的那么做了，你就会激怒几百万人。而且你最终并不会成功，因为那几百万人根本不会用你的新玩意，他们会坚持用旧的。</p>
<p>所以我说那句话，是在表达我对那些过度简化复杂问题的人的挫败感。有些人认为他们不需要学习编程就能编程；他们认为不需要学习工程学就能成为工程师；他们认为不需要知道如何管理一家公司或一个国家就能成为政治家。</p>
<p>这种极度粗暴的“过度简化”让我非常恼火。我可能不应该轻易表现出恼火，我很少这样做，但在那种特定情况下，我的挫败感确实显露出来了。</p>
<p><strong>Ryan Peterman</strong>：当面对有人觉得 C++ 很难学时，似乎有些人的视角是“编程应该平易近人，任何人都能学编程”。但我认为你表达的观点是：C++ 并不一定是为每个人准备的。它是为“严肃的程序员”准备的。</p>
<p><strong>Bjarne Stroustrup</strong>：是的。《C++ 编程语言》第一版的第一句话就是：“C++ 被设计出来，是为了让严肃的程序员（serious programmer）的生活更加愉快。”我后来去掉了最初版本里的“专业程序员（professional）”这个词，因为我见过一些业余爱好者同样极其、极其优秀。</p>
<p>一个“严肃的程序员”通常是在为别人编写程序。如果你只为你自己编程，那无所谓，这是你自己的事。如果你为你的朋友编程，你可能会失去朋友。但如果你在为一百万人构建系统，你的失误可能会给世界带来真实的伤害。C++ 就是为处理这种量级的问题而生的。</p>
<p>Guido van Rossum 在构建 Python 时，明确的目标就是让许多人甚至所有人都能编程，而且他做得极其成功。而我设计 C++ 的目标，是为严肃的程序员、工程师和数学家等群体打造一个极其出色的强力工具，我也成功了。</p>
<p>这只是两个完全不同的问题领域。记住我们一开始聊到的：首先认清你面临的是什么问题，然后再去从什么有用、什么没用中学习。</p>
<p><strong>Ryan Peterman</strong>：回首 C++ 及其整个发展历程，有没有哪一部分让你觉得“噢，那是个错误”，或者说你在设计中汲取了某种教训？</p>
<p><strong>Bjarne Stroustrup</strong>：在无数个时刻我都学到了教训。</p>
<p>我认为大多数实验性的想法从未真正进入过 C++ 标准。这就是为什么你需要做实验，为什么你需要首批的“小白鼠”用户。我认为我在宏观上把握住了这门语言的主要方向。回过头看，我几乎可以改进里面的每一个微小细节。但是，稳定性和兼容性是绝对不可或缺的基石。</p>
<p>如果你做了一个无关紧要的修改，只会惹恼少数几个人，那无伤大雅。但如果你做了一个会破坏向后兼容性的重大修改，你会惹怒海量的人，而且这根本行不通。因为比方说一百万人会直接拒绝升级，继续坚持他们原有的做法。</p>
<p>所以我一直努力在不破坏现有生态的前提下，让这门语言逐渐生长。</p>
<p>有一件事总是反反复复地发生，我都解释麻木了。人们走到我面前对我说：“C++ 太复杂了。你必须简化它。对了，顺便说一下，我极度需要这两个新特性。我昨天就需要了。你必须在做简化的同时把这两个特性加给我。而且无论你做什么，绝对不能弄坏我现有的代码，我有上百万行呢。”</p>
<p>这种“既要又要还要”的逻辑根本行不通，在现实中是不可能的。</p>
<p>这也是为什么我目前正致力于编码指南（Coding Guidelines）以及 Profiles（被强制执行的指南集合）的工作。通过这种方式，你可以自行设计一个 Profile 配置，以确保你在开发时能够使用你所需的所有新库，同时编译器会保证你不会误用在你的特定领域内那些不必要的、危险的旧特性。</p>
<p><strong>Ryan Peterman</strong>：对于想要学习 C++ 的人，我想大家普遍会问：你最推荐的技术书籍是哪一本？</p>
<p><strong>Bjarne Stroustrup</strong>：去学习现代 C++（Modern C++）。有一本书是我在教本科生时写的——这纯属偶然，我本来没打算写——《C++ 程序设计原理与实践》（Programming: Principles and Practice Using C++）。这是一本写给本科生的大厚书。最新的第三版已经没那么厚了，因为语言本身得到了改进，我用更少的文字就能把核心思想讲清楚了。</p>
<p>使用最新的 C++，从一开始就学习“现代”的方法。千万不要以学习如何编写糟糕的 C 语言作为起点。令人遗憾的是，现在很多课程依然告诉你“先学 C”。于是你学了一大堆宏操作、<code>malloc</code> 以及裸指针，然后告诉你“以后你再去学如何使用 <code>vector</code> 和 <code>string</code> 以避免这些问题”。</p>
<p>Profiles 的存在，正是为了在编译器和静态分析器层面，为这种“现代思维方式”提供系统级的支持。教育工作者们也一直在呼吁这种支持。很多人以为 Profile 只是用来处理内存安全和性能的。不是的，它必须为人们提供一个更好的工具，不仅用于实际的特定领域开发，更用于正确的教学。</p>
<p><strong>Ryan Peterman</strong>：最后一个问题，如果你能乘坐时光机回到职业生涯的起点，给自己一些建议，你会说什么？</p>
<p><strong>Bjarne Stroustrup</strong>：哦天哪。这是个经典的时光机问题。我有时也会在课上给我的学生布置这种题。规则是：“如果你有一台时光机，先回到过去给 Dennis 提点建议；然后往后跳 10 年，回来给我提点建议。”这是个很好的思维训练。我经常能从学生的答案里听到一些非常绝妙的想法和建议。</p>
<p>对于我自己……我认为我应该更加坚决地抵制 C 语言中内置类型之间的隐式窄化转换（narrowing conversions）。我当时确实抗争过，但在贝尔实验室里被比我更资深、更有经验的人给否决了。现在回想，我当时应该在那一点上走得更远，绝不退让。</p>
<p>此外，我本应该推迟 C++ 的正式发布，直到我能够构建出类似“模板（templates）”的机制。这样我就能随之发布一个更好的标准库。虽然在当时那肯定依然不够完美，但它至少会让人们一开始就养成使用标准库的习惯。当时每个人都在造自己的轮子写标准库，后来我们非常幸运地被 Alex Stepanov 开发的 STL 拯救了。但那真的是靠运气，因为我犯了一个错误，没有等到我能构建出一个优秀的 <code>vector</code> 和类层次结构后再发布。</p>
<p>最后一点，如果我当年能拥有我现在对标准委员会和臃肿官僚机构的认知——你知道，我们现在的子工作组数量比当初标准委员会成立时的总成员数还要多——我会非常努力地尝试建立一个某种形式的核心指导小组（steering group）。</p>
<p>这样所有人都可以提出建议。但我们不是让 500 个人一起来投票决定。我们会从一个 500 人的社区收集所有的提案，然后由一个由五六个拥有极其丰富经验、且真正关怀这门语言整体架构的人组成的核心小组，基于这些提案做出最终的决策。类似这样的机制。但我当年显然没有足够的经验和知识来提出这样的建议。</p>
<p>注意，我刚才完全没有提到“工具（Tools）”。C++ 在周边生态工具方面存在弱点。这是因为它诞生于一个极其早期的时代，当时的工具很简陋，计算能力极其有限，内存也少得可怜。所以在当时我根本不可能做出现在这样的工具链。</p>
<p>在给学生布置时光机作业时，我总是加上一个约束条件：“尽量确保你的建议在当时的历史条件下是真正‘能够被执行’的。”</p>
<p>如果我只凭空想象说“我想要这个完美特性”，那么很多东西在当时的条件下根本做不出来，可能要等到 20 年后才能实现，如果那样的话 C++ 就胎死腹中了。世界上有很多语言在设计之初就追求极致的完美，试图为“未来的计算机”和“未来的程序员”量身定制。但它们绝大多数都死掉了。因为等它们花 10 年时间把语言打磨出来时，当初它们所锚定和构想的那个世界，早就已经不复存在了。</p>
<p><strong>Ryan Peterman</strong>：我能想象在当时的环境下，要坚持自己的立场肯定非常艰难，因为贝尔实验室的那些人资历太深了。</p>
<p><strong>Bjarne Stroustrup</strong>：我失败了。我尝试过。</p>
<p>很明显你不希望发生隐式的窄化转换（比如浮点数悄无声息地变成整数并丢失精度）。我去年甚至还写了一篇论文，讨论在今天的标准库层面如何彻底消除它们。但这确实是 C 和 C++ 类型系统中的一个根本性缺陷。</p>
<p>它之所以存在，是因为当时像 Dennis Ritchie 和 Unix 核心团队那些人，极度需要一种能够同时、顺滑地处理整数和浮点数的方式。他们没考虑使用显式类型转换，他们觉得显式转换写起来太笨重了。他们实际上是在引入了浮点数和整数大约五年后，才在语言中加入了“类型转换（casts）”机制。而你显然必须能够把一个浮点数变成整数，对吧？所以他们就允许在任何可能的地方进行隐式的自动转换。包括把整数转成字符之类也会产生问题。</p>
<p>但因为你是在编写最底层的核心系统软件，你不想写繁琐的代码，你也负担不起任何“运行时检查”的开销。所以这些缺陷在远早于我加入贝尔实验室之前，就已经作为底层基石被确立下来了。我试图改变它的努力最终失败了。</p>
<p><strong>Ryan Peterman</strong>：听起来这并不是毫无理由的。它是为了在极其有限的硬件资源下节省开销。</p>
<p><strong>Bjarne Stroustrup</strong>：是的，他们当时根本没有足够的硬件资源来处理这种严格的类型安全。机器太小了。他们确实构建了 <code>lint</code> 这个静态检查工具来尝试处理部分问题。</p>
<p>另一个不可忽视的背景是，那一代的程序员群体，比今天普通的开发者要聪明得多，经验也丰富得多。今天我们面对的是大数定律。</p>
<p>我想我最近看到的数据是，全球现在的软件开发者大约有 4700 万人。而在 Unix 诞生的那个年代，全世界的程序员加起来可能就几十个。在那个年代，如果一个人不是从顶尖名校拿了博士学位出来的，那他大概率是个未经雕琢的旷世天才（在那时拿博士学位甚至比成为天才还要容易些）。</p>
<p>所以，他们是为了一群截然不同的人、一套截然不同的硬件机器、去解决一套截然不同的问题。</p>
<p>哎，但这在今天确实成了一个让人头疼的问题，至今依然如此。</p>
<p><strong>Ryan Peterman</strong>：太棒了。非常感谢您抽出宝贵的时间，教授。我非常感激。</p>
<p><strong>Bjarne Stroustrup</strong>：好的，谢谢。</p>
