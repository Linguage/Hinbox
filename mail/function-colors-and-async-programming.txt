<h2>摘要</h2>
<p>这篇文章用红色函数和蓝色函数的比喻，解释异步编程为什么会让代码世界分裂成两套规则。回调、Promise、async await 都在缓解痛苦，但没有完全消除同步与异步之间的边界。真正的问题在于调用栈如何保存与恢复，而线程、协程、goroutine 这类机制能从根上减少这种割裂。</p>
<h2>内容框架与概述</h2>
<p>文章先虚构了一门带有函数颜色的语言。每个函数必须是红色或蓝色，调用方式也不同，而且蓝色函数不能调用红色函数。更麻烦的是，红色函数调用成本更高，但核心库里偏偏存在必须使用的红色函数。这个荒诞设定把程序员每天面对的异步问题放大成一套清晰规则。</p>
<p>随后，红色函数的真实含义揭开：它们就是异步函数。Node.js 中的回调、Promise、future 都是在处理异步返回值，但它们让函数调用、错误处理、控制流、组合方式发生变化。async await 让异步代码写起来舒服很多，却仍然保留了两种函数世界：同步函数返回普通值，异步函数返回包装后的未来值。</p>
<p>最后，文章把问题推到调用栈层面。异步 IO 需要在操作完成后恢复现场，但普通调用栈已经被清空，于是语言只能用回调、闭包、Promise 或编译器转换来保存状态。Go、Lua、Ruby 这类有 goroutine、coroutine、fiber 的语言可以挂起并恢复独立调用栈，因此不必把函数分成两种颜色。</p>
<h2>核心概念及解读</h2>
<h3>Red Function</h3>
<p>红色函数，对应异步函数。它不能像普通函数那样直接返回结果，而是通过回调、Promise、Future 或 Task 交出结果。它的麻烦在于，一旦某个函数调用了异步函数，调用链上方也常常要跟着变成异步。</p>
<h3>Blue Function</h3>
<p>蓝色函数，对应同步函数。它直接返回值，能自然参与表达式、条件判断、异常处理和普通控制流。它的问题在于，一旦需要等待异步结果，就无法直接调用红色函数拿到最终值。</p>
<h3>Callback Hell</h3>
<p>回调地狱，是异步编程中层层嵌套回调导致的代码结构问题。它表面上是缩进和可读性问题，底层是程序员手动保存未来要继续执行的上下文。</p>
<h3>Continuation Passing Style</h3>
<p>续体传递风格，是把后续要执行的逻辑包装成函数传下去。编译器内部常用这种形式处理控制流，但让程序员手写这种代码会非常别扭。Node.js 回调模型本质上就让开发者手动写了很多这种结构。</p>
<h3>Reified Callstack</h3>
<p>实体化调用栈，意思是把调用栈保存成可以挂起和恢复的对象。线程、协程、goroutine 都能做到类似效果，所以代码看起来像同步写法，但运行时仍然可以在等待 IO 时切换去执行别的任务。</p>

<h1>函数颜色这个比喻在讲什么</h1>
<h3>红色函数与蓝色函数</h3>
<p>用一门虚构语言做比喻：所有函数都有颜色，要么红色，要么蓝色。调用红色函数和调用蓝色函数的语法不同，而且蓝色函数不能直接调用红色函数。只要代码里碰到红色函数，周围的函数就容易被迫一起变红。</p>
<p>这个设定看起来荒唐，但它精准对应了同步函数和异步函数的分裂。同步函数能直接返回结果，异步函数只能通过回调、Promise、Future、Task 之类的方式在未来交出结果。问题不在于语法丑，而在于整个调用链都会被这种差异牵着走。</p>
<h2>异步函数会把代码世界分成两半</h2>
<h3>同步函数的自然性</h3>
<p>同步函数的行为符合人的直觉：调用它，等待它执行完，拿到结果，然后继续往下走。它能放进表达式、条件判断、循环、异常处理里，和其他代码自然组合。</p>
<p>比如一个函数返回数字，你就可以直接拿这个数字做加法、比较、传给别的函数。调用栈也很清楚：A 调 B，B 调 C，C 返回，B 继续，A 继续。</p>
<h3>异步函数的传播性</h3>
<p>异步函数的问题是，它不能立刻给出结果。它说的是：我先返回，真正的结果之后再通知你。于是调用它的函数也不能直接返回最终结果，只能变成异步函数，继续把这个等待过程往上传。</p>
<p>这就是所谓颜色污染。一个底层函数变红，上层函数常常也要变红，再上层继续变红。最后不是某个函数用了异步，而是整段代码结构都被异步改写了。</p>
<h2>回调地狱不是单纯的缩进问题</h2>
<h3>回调是在手动保存后续流程</h3>
<p>Node.js 早期的回调写法，会让代码不断向右缩进。表面看是代码难看，真正的问题是程序员在手动保存程序的下一步。</p>
<p>正常情况下，调用栈会记住程序执行到哪里。异步 IO 要把控制权交还给事件循环，调用栈会被清空。为了之后还能接着执行，只能把后续逻辑塞进回调函数里。</p>
<h3>程序员被迫像编译器一样写代码</h3>
<p>这种写法接近 continuation passing style，也就是续体传递风格。它在编译器内部有用，但让日常开发者手写，就会非常反人类。</p>
<p>每一步异步操作后面都要手动包一层函数，每一层函数又捕获上一层的变量。代码还能跑，但结构变成了一串手工拼起来的未来步骤。维护者读起来累，改起来更容易出错。</p>
<h2>Promise 和 Future 只是减轻痛苦</h2>
<h3>Promise 把回调包装成对象</h3>
<p>Promise 或 Future 把异步操作变成一个一等对象。它能表示某个未来才会完成的任务，也能组合多个异步任务。比裸回调好一些，错误处理和链式调用也规整一些。</p>
<p>但它没有消除同步与异步的边界。你拿到的仍然不是结果本身，而是一个包装结果的对象。要真正拿到值，还是要进入异步流程。</p>
<h3>then 只是换了一种回调形式</h3>
<p>使用 Promise 后，代码可能从嵌套回调变成链式 then。结构看起来顺眼了一点，但后续逻辑还是被塞进函数里，只是换了一个容器。</p>
<p>所以 Promise 改善了写法，没有改变问题的根。异步世界依然是红色世界，同步世界依然是蓝色世界，两者之间仍然有墙。</p>
<h2>async await 解决了语法痛点，但没有消除颜色</h2>
<h3>await 让异步代码接近同步写法</h3>
<p>async await 最大的好处是让异步代码看起来像同步代码。可以用普通顺序写法，可以放进控制流，也能和 try catch 配合。比回调和 Promise 链都更容易读。</p>
<p>从开发体验看，这是巨大进步。程序员终于不必手动把每一步后续逻辑写成函数，编译器会帮你做转换。</p>
<h3>async 仍然会改变函数类型</h3>
<p>问题还在：用了 await，函数就要变成 async。async 函数返回的不是普通值，而是 Promise、Future 或 Task 这类包装值。</p>
<p>这意味着颜色还在。调用异步函数的人仍然要知道它是异步的，仍然可能被迫也变成异步。async await 主要解决了红色函数难调用的问题，没有解决红色函数和蓝色函数同时存在的问题。</p>
<h2>高阶函数会放大颜色问题</h2>
<h3>filter 这类函数会遇到颜色选择</h3>
<p>高阶函数接受函数作为参数，比如 filter 接受一个 predicate。问题来了：这个 predicate 是同步还是异步？</p>
<p>如果 filter 是同步的，它不能自然处理异步 predicate。如果 filter 是异步的，所有调用 filter 的地方又要面对异步返回值。一个普通的抽象 suddenly 变成了 API 设计难题。</p>
<h3>代码复用也会被颜色牵制</h3>
<p>不只是高阶函数，普通代码复用也会遇到同样的问题。你把一段逻辑抽成函数，如果这段逻辑内部调用了异步 API，那这个新函数也要变成异步。</p>
<p>随后，原本调用它的地方也要调整。一个小小的实现细节，可能一路影响到上层结构。异步不只是函数内部的事，它会变成接口的一部分。</p>
<h2>真正的问题是调用栈如何保存</h2>
<h3>异步 IO 需要离开当前调用栈</h3>
<p>异步 IO 的核心矛盾是：操作系统完成 IO 需要时间，程序不能傻等，否则性能会差。于是语言运行时会把控制权交还给事件循环，让别的任务先运行。</p>
<p>但一旦函数返回，当前调用栈就没了。等 IO 完成后，程序还要知道从哪里继续。这个继续执行的位置、局部变量、上下文，都需要被保存。</p>
<h3>回调、Promise、async await 都是在保存现场</h3>
<p>回调把后续逻辑放进闭包。Promise 把异步结果和后续操作包装起来。async await 由编译器把函数拆成多段，等异步完成后再恢复。</p>
<p>这些方案本质都在做同一件事：把原本应该由调用栈保存的信息，搬到堆上，用函数对象或状态机保存起来。区别只是由程序员手写，还是由编译器代劳。</p>
<h2>线程、协程和 goroutine 的优势</h2>
<h3>独立调用栈可以直接挂起</h3>
<p>如果语言有线程、协程、fiber、goroutine 这种独立调用栈机制，就可以在 IO 等待时挂起当前执行流。调用栈不用清空，等 IO 完成后再恢复。</p>
<p>这样代码可以保持普通同步写法，同时运行时仍然能切换去执行别的任务。程序员不必把函数分成红色和蓝色两类。</p>
<h3>Go 把并发从函数颜色中拿出来</h3>
<p>Go 的 IO API 看起来像同步调用：调用、等待、返回结果。但当 goroutine 等待 IO 时，运行时可以调度其他 goroutine 继续执行。</p>
<p>这样并发变成程序建模方式，而不是刻在每个函数签名上的颜色标签。你可以决定程序如何并发，但不用让每个函数都承担同步或异步的身份负担。</p>
<h2>对语言设计的批评</h2>
<h3>异步 API 容易把复杂性推给开发者</h3>
<p>很多语言把异步能力包装成 API 层面的差异：这里返回普通值，那里返回 Promise；这里直接调用，那里需要 await。结果是语言把运行时调度问题暴露给了开发者。</p>
<p>开发者不得不在业务逻辑之外，持续处理函数颜色、返回类型、错误传播、调用链改造这些问题。</p>
<h3>好的并发模型应该减少接口污染</h3>
<p>更理想的设计，是让等待 IO 这件事由运行时处理，而不是让每个函数签名都暴露同步或异步的差异。调用者关心的是结果，运行时关心的是如何调度。</p>
<p>这也是为什么带有独立调用栈的并发模型更有吸引力。它让程序结构接近人的思考方式，同时保留高并发执行能力。</p>
<h2>对现代编程经验的提醒</h2>
<h3>async await 好用，但不要把它当成终点</h3>
<p>async await 的确比回调和 Promise 链舒服得多。它降低了异步代码的书写成本，也让错误处理和控制流更接近普通代码。</p>
<p>但它没有让异步消失。函数签名、调用链、返回类型仍然会暴露异步身份。大型代码库里，这种差异会持续影响抽象、复用和 API 设计。</p>
<h3>异步边界要谨慎设计</h3>
<p>一旦某个模块把异步暴露到接口层，调用者就必须处理它。底层 API 的一个选择，可能让上层大量代码跟着调整。</p>
<p>所以异步边界最好集中、明确、稳定。能封装就封装，能把等待逻辑放在少数入口就放在少数入口。不要让红色一路蔓延到不该关心并发细节的业务层。</p>
<h2>核心判断</h2>
<h3>函数颜色问题不是语法洁癖</h3>
<p>这不是嫌弃回调难看，也不是偏好某种语言风格。真正的问题是：语言把异步等待变成了一种函数类型差异，然后让这种差异沿着调用链扩散。</p>
<h3>并发模型决定代码结构</h3>
<p>一门语言怎么恢复执行现场，决定了程序员怎么写代码。没有独立调用栈，就要靠回调、Promise、状态机来保存现场。有独立调用栈，就可以让等待看起来像普通调用。</p>
<p>所以异步编程的痛点，本质上是运行时模型和语言抽象共同造成的。语法糖能止痛，调用栈模型才决定病根在哪里。</p>
