<p>第二部分集中在后台智能体的架构。核心问题包括智能体运行在哪里、机器环境如何准备、密钥如何隔离、仓库依赖如何初始化、Docker 是否够用、为什么完整 VM 对真实应用测试更有价值。Devin 采用大脑与机器分离的设计，把决策系统和执行环境拆开，以降低权限、密钥和安全风险。</p>
<p>第三部分进入企业使用层面。智能体要真正进入工程体系，不能只会写代码，还要能接入 GitHub、Slack、日志系统、知识库、生产只读数据和代码审查流程。访谈还讨论了记忆系统、自动生成经验、多人协作、PM 从 Slack 发起 PR、SRE 自动排障，以及无人审查式 vibe coding 导致代码库快速劣化的问题。</p>
<h2>核心概念及解读</h2>
<h3>Async Agents，异步智能体</h3>
<p>异步智能体是后台运行的 AI 工程执行者。它不要求开发者一直盯着屏幕，而是在云端拿到任务、仓库、运行环境、测试工具和权限后，自己推进工作。它的目标是从一句规格说明走到可审查的 PR。</p>
<h3>Spec to PR，从规格到拉取请求</h3>
<p>这是当前编码智能体最重要的生产流程之一。人类写清楚需求，智能体负责理解代码库、修改代码、运行测试、生成 PR，并根据评论继续修改。这里的难点不只在写代码，还在理解工程上下文、测试路径和团队习惯。</p>
<h3>Brain Machine Separation，大脑与机器分离</h3>
<p>Devin 的关键架构思路。大脑负责推理、规划和调用工具，机器负责执行代码、运行 shell、打开浏览器、测试应用。这样可以把高权限决策系统和具体运行环境隔开，减少密钥泄露与权限混乱。</p>
<h3>Repo Setup，仓库环境初始化</h3>
<p>后台智能体能不能工作，很大程度取决于仓库能不能跑起来。依赖、密钥、数据库、微服务、Docker Compose、测试数据、Feature Flag，这些都要准备好。对许多公司来说，让工程环境变得可复现，本身就是迈向智能体开发的第一步。</p>
<h3>Codebase Decay，代码库劣化</h3>
<p>如果完全让 AI 自动合并代码，不做审查，代码库会很快变乱。重复组件、分散实现、奇怪的 helper、过度 if else、局部修补会不断堆积。AI 会学习已有代码中的坏模式，所以人类仍然要守住架构边界、审查质量和长期可维护性。</p>

<h1>内容要点</h1>
<h2>一、后台智能体成为软件开发的新中心</h2>
<h3>从 IDE 内辅助，到云端独立执行</h3>
<p>早期 AI 编码工具的价值在于加快开发者写代码的速度，比如补全、生成片段、解释函数。人在 IDE 里，模型在旁边帮忙，开发者需要不断接受、拒绝、调整和提交。这个阶段的瓶颈仍然是人类开发者的本地工作流。</p>
<p>后来出现本地代理，Claude Code、Windsurf、Cursor agent 这类工具可以在终端里连续行动，能读文件、改代码、运行命令、修复错误。它们已经从代码补全进入任务执行，但多数情况下仍然离不开开发者的持续盯盘。</p>
<p>现在的变化是后台智能体。人给出规格说明、仓库、机器、shell、浏览器、测试入口和反馈机制，智能体在云端独立完成工作。开发者从写代码的人，逐渐转向分配任务、配置环境、审查结果的人。</p>
<h3>异步智能体改变开发节奏</h3>
<p>异步智能体的关键价值在于它不占用开发者的前台注意力。过去开发者和模型是一问一答，像两个人挤在一张桌子前写代码。后台智能体则像被分配到另一台机器上的队友，拿着任务去做，做完后提交 PR，等待审查。</p>
<p>这种模式让软件开发更接近任务调度。开发者可以同时安排多个任务，不必守着每一个模型响应。真正的变化不在于 AI 会不会写函数，而在于它能不能从任务说明走到可合并的工程结果。</p>
<h2>二、规格到 PR 成为可用工作流</h2>
<h3>模型能力在 2025 年底出现明显跃迁</h3>
<p>2025 年 12 月前后，Opus 4.5 和 GPT 5.2 这类模型达到了新的自治水平。过去需要人类不断扶着模型走，现在只要规格说明足够清楚，模型就能较少干预地完成从需求到 PR 的过程。</p>
<p>这个跃迁让后台智能体从实验品变成真实工程工作流。很多团队开始重新评估开发方式：是否还需要所有工作都发生在本地 IDE 中，是否可以把一部分任务直接交给云端智能体完成。</p>
<h3>Devin 的使用增长说明工作流开始成立</h3>
<p>Cognition 内部的 Devin 使用数据变化很大。合并 PR 数量在短时间内增长多倍，Devin 在 Cognition 仓库中的提交占比从年初的 16% 上升到 80%。这说明它已经进入日常工程生产，而不是只做 demo。</p>
<p>这个数字的意义在于，智能体不只是帮忙写零散代码，而是在真实代码库中承担大量改动。团队开始把它当作可调度的工程资源，而不是临时工具。</p>
<h3>好规格比随口指令更重要</h3>
<p>从规格到 PR 能成立，有一个前提：任务说明必须足够清楚。后台智能体并不能自动弥补模糊需求。如果需求边界、验收标准、依赖关系和测试路径不清楚，模型会用自己的猜测填空，结果容易偏掉。</p>
<p>这会倒逼团队把需求写得更工程化。任务需要说明修改目标、相关文件、预期行为、测试方式、不能破坏的边界。AI 时代并没有让规格说明消失，反而让规格说明变成更高杠杆的工作。</p>
<h2>三、OpenInspect 的出现说明后台智能体正在基础设施化</h2>
<h3>很多公司开始自建 Devin</h3>
<p>背景智能体的门槛正在下降。LangGraph、Pydantic、Flue，以及 Anthropic、Gemini、OpenAI、Amazon 等提供的托管智能体能力，让公司更容易搭建自己的后台代理系统。Shopify、Stripe、Paradigm、Razorpay、Ramp 等团队都在建设类似系统。</p>
<p>这带来一个张力：一方面有 Cognition 这种高估值公司做完整产品，另一方面开源和内部自建也越来越可行。后台智能体正在从单一产品，变成企业工程基础设施的一部分。</p>
<h3>OpenInspect 解决的是团队协作中的具体摩擦</h3>
<p>OpenInspect 的起点来自真实使用问题。比如 PM 在 Slack 里启动了一个 AI 编码会话，但工程师接手时看不到完整上下文，只能靠复制粘贴传递信息。这种协作断裂让后台智能体很难进入团队流程。</p>
<p>OpenInspect 想提供一个开源基础，让团队可以搭建自己的云端后台代理系统，并按公司内部需求改造。它不急于做成 20 美元一席的 SaaS 产品，因为这个位置商业化困难，模型层、沙箱层、云资源层都有人在收费，中间层如果没有完整生态，很容易被压缩。</p>
<h3>开源后台智能体更适合需要定制的团队</h3>
<p>很多公司会把后台智能体视为内部基础设施。它需要接入公司自己的权限系统、仓库结构、日志、数据库、知识库、工单系统和安全流程。开源方案的价值在于可以 fork，可以改，可以部署到自己的环境中。</p>
<p>这类系统的竞争点不只是模型能力，还包括企业集成、权限管理、环境复现、审查流程和组织采用。Cognition 卖的不只是 Devin 本身，还包括基础设施、入门支持、集成能力和团队使用方法。</p>
<h2>四、后台智能体的核心架构问题</h2>
<h3>智能体运行在盒子里，还是盒子外</h3>
<p>后台智能体有一个基础架构选择：让智能体本身运行在沙箱环境里，还是让它在外部控制平面运行，再通过工具调用操作沙箱。</p>
<p>运行在盒子里比较简单。状态都在一个环境中，开发和调试更直接。但风险是密钥、权限和执行环境混在一起。AI 行为有不确定性，一旦工具链或提示失控，就可能泄露密钥或执行不该执行的操作。</p>
<p>运行在盒子外更复杂。智能体大脑在外部，机器只是它的手。这样需要管理更多状态，但安全边界更清楚。Devin 从一开始就采用大脑与机器分离的设计。</p>
<h3>大脑与机器分离降低权限风险</h3>
<p>Devin 的架构把推理系统和执行机器拆开。大脑负责规划、理解任务、决定调用什么工具。机器负责运行代码、执行 shell、打开浏览器、测试应用。</p>
<p>这个设计可以让机器只拿到被限定范围内的密钥。比如某个用户只能访问某些 GitHub 权限，那么放进机器里的凭证也只覆盖这些权限。大脑本身不暴露给机器，机器上的代码也无法轻易接触更高权限系统。</p>
<p>这种设计对于企业尤其重要。公司不可能把所有生产密钥丢进一个 AI 可以随便操作的环境中。权限需要按用户、任务、仓库、工具和安全级别切分。</p>
<h3>控制平面会变得越来越重要</h3>
<p>当系统只跑一个简单任务时，架构可以粗糙一点。但当后台智能体需要处理 Slack、GitHub、PR、日志、数据库、知识库、长期任务和多个子代理时，控制平面就会成为核心。</p>
<p>控制平面需要知道哪些任务正在运行，哪些 PR 已经打开，哪些评论需要处理，哪些任务被合并，哪些失败了，失败原因是什么。这已经接近一个智能体操作系统，而不只是一个提示词加沙箱。</p>
<h2>五、仓库环境初始化是最难的工程问题之一</h2>
<h3>让代码跑起来，比让模型写代码更难</h3>
<p>后台智能体要真正修改代码，首先要把仓库跑起来。许多公司内部开发环境很混乱，依赖怎么装、密钥找谁拿、数据库怎么连、服务怎么启动，常常存在于某个老员工脑子里。</p>
<p>对人类来说，可以去问同事。对智能体来说，这种隐性知识会直接卡住任务。Repo setup 变成长期难题：如何让每个仓库在云端可复现、可启动、可测试、可恢复。</p>
<h3>Docker Compose 有帮助，但不够完整</h3>
<p>很多团队用 Docker Compose 管理本地开发依赖，这对智能体有帮助。它能让数据库、缓存、后端服务、mock 服务以较统一的方式启动。</p>
<p>但 Docker 不是完整答案。Docker 容器本身并不是真正强安全边界，而且真实应用常常需要在容器中再运行容器，会引出 Docker in Docker 的复杂性。对于大型应用、桌面应用、移动开发、浏览器测试，单纯容器方案会遇到限制。</p>
<h3>完整 VM 更适合真实应用测试</h3>
<p>Devin 采用完整 VM 的原因在于，后台智能体需要运行真实应用、打开浏览器、点击页面、录制结果、启动复杂服务，甚至支持 Android、macOS、Windows 等特定环境。</p>
<p>VM 的问题是启动、暂停、恢复、快照都要优化。普通云 VM 并不是为频繁启动和恢复设计的。Cognition 早期就需要解决快速恢复机器状态的问题，否则每次唤醒智能体都要等待很久。</p>
<h2>六、测试比电脑操作难得多</h2>
<h3>电脑操作只是测试的一小部分</h3>
<p>很多人谈 AI 测试时容易盯着电脑使用能力，比如能不能点击按钮、识别坐标、操作浏览器。这个能力重要，但只是表层。</p>
<p>真正难的是：智能体如何知道要测试什么，如何启动相关服务，如何打开对应功能，如何准备账号权限，如何开启 feature flag，如何构造触发条件，如何判断结果是否正确。</p>
<h3>测试需要理解代码库和业务流程</h3>
<p>如果一次改动同时涉及前端、后端和深层服务，测试就会变得复杂。智能体必须知道这些服务如何协作，哪个版本的代码要启动，什么数据能触发新逻辑，什么页面能看到结果。</p>
<p>这不是单纯视觉模型问题，而是工程推理问题。它需要代码库上下文、运行环境、业务流程和测试目标共同参与。某些复杂场景下，一个前沿模型也未必能独立完成，需要多个模型或多个步骤配合。</p>
<h3>视频验证让合并决策更可信</h3>
<p>Devin 会在 PR 完成后提供测试视频，展示它测试了哪些行为、鼠标怎么操作、页面如何变化。视频下方还会标注当前测试目标，让人知道自己正在看什么。</p>
<p>这类验证改变了审查体验。过去开发者看代码来判断能不能合并，现在可以先看行为是否符合预期。对于某些简单改动，视频证据足够让人快速建立信心。</p>
<h2>七、GitHub 工作流正在被智能体重塑</h2>
<h3>PR 不只是交付物，也是对话界面</h3>
<p>后台智能体完成任务后通常会创建 PR。但真正好用的体验不止是自动开 PR，还要能在 GitHub 评论中继续对话。开发者评论哪里需要改，智能体能收到、理解、修改、再回复。</p>
<p>这让 GitHub 成为人机协作界面。智能体不再只是一次性提交代码，而是进入代码审查回路。</p>
<h3>AI 代码审查会成为后台智能体的关键部件</h3>
<p>Devin Review 和 OpenInspect 的 GitHub reviewer 都在尝试把 AI 审查纳入系统。AI 可以评论代码问题，也可以根据评论继续修复。</p>
<p>难点是避免低质量评论和循环修复。智能体需要判断哪些评论值得处理，哪些评论可能是误判。更成熟的智能体甚至会反驳人类或另一个 AI 的评论，这说明它开始具备工程判断能力，而不只是机械服从。</p>
<h3>自动合并仍然危险</h3>
<p>完全不看代码、完全自动合并，会带来代码库劣化。短期看速度很快，长期看重复实现、风格漂移、边界混乱会迅速累积。</p>
<p>更可行的方式是保留审查机制。人类重点看架构边界、模块接口、长期可维护性和安全风险。AI 可以承担初步审查、重复性检查和修复建议，但不能完全替代工程判断。</p>
<h2>八、企业集成比 MCP 更复杂</h2>
<h3>MCP 解决工具连接，但不等于好体验</h3>
<p>MCP 让智能体接入外部工具更容易。理论上，给模型一个 Slack MCP，它就能发消息；给它数据库 MCP，它就能查数据。</p>
<p>但企业级体验不止是能调用工具。Slack 集成需要处理 webhooks、线程回复、通知频率、上下文共享、权限限制和消息风格。简单工具连接无法自动给出稳定、自然、不打扰团队的协作体验。</p>
<h3>高频核心工具值得一方集成</h3>
<p>如果某个集成几乎每个任务都会用，比如 Slack、GitHub、日志系统、生产只读数据库，那么公司最好拥有更高控制权。通用 MCP 适合快速接入，核心流程需要更深的定制。</p>
<p>Cognition 的经验是，很多场景最终还是要做一方集成。因为一旦 MCP 规范变得太复杂，它就失去了简单连接的优势；但如果保持简单，又覆盖不了企业复杂需求。</p>
<h3>智能体需要进入公司真实系统</h3>
<p>后台智能体要有实际价值，不能只在仓库里改代码。它需要读取日志、查询只读生产数据、理解 Confluence 或内部知识库、接触工单系统、接收 Slack 指令、追踪 PR 状态。</p>
<p>这意味着它会越来越像企业内部的工程协作者。权限、审计、合规、数据隔离会成为核心问题。</p>
<h2>九、记忆系统仍然没有被彻底解决</h2>
<h3>记忆生成和检索都很难</h3>
<p>智能体需要记住团队习惯、代码库约定、常见坑、偏好流程和过去反馈。但记忆不是简单存文本。难点有两个：该记住什么，以及什么时候取出来用。</p>
<p>如果记忆过细，系统会记住一次性细节。比如某次让它开 draft PR，它可能以后都这么做。如果记忆过粗，它又失去作用。检索也麻烦，记忆太多会塞爆上下文，取错记忆会误导任务。</p>
<h3>自动生成记忆更符合真实使用习惯</h3>
<p>Devin 的 Knowledge 系统会在用户纠正它时主动询问是否记住。绝大多数记忆来自这种自动生成，而不是用户手写长文档。原因很简单，工程师很少愿意专门坐下来给 AI 写使用手册。</p>
<p>这种方式比较贴近日常工作。人类在互动中纠正智能体，智能体把稳定偏好和团队规则沉淀下来。它像新人入职时不断记笔记，只是这些笔记需要可编辑、可删除、可更新。</p>
<h3>文件系统式记忆可能更适合智能体</h3>
<p>访谈中提到一个方向：把记忆做得更像文件系统，让智能体自己浏览、grep、维护和更新。现在的模型很擅长操作文件，因此 memory.md、技能文件、项目说明文档这类形式可能比黑盒检索更好用。</p>
<p>这种记忆系统也更容易审查。团队可以看到智能体记住了什么，删掉错误信息，更新过时规则，避免隐性偏差长期影响工程结果。</p>
<h2>十、多智能体有价值，但实际使用仍偏克制</h2>
<h3>子代理更像上下文管理工具</h3>
<p>现在很多所谓多智能体，更接近让主代理派一个子任务出去。比如让子代理查找文件、阅读某部分代码、分析某个实现，然后把结果压缩返回给主代理。</p>
<p>这种方式的价值在于节省上下文。子代理消耗大量 token 做探索，最后只把结论交回来。它像一个工具调用，而不是一群智能体自由聊天。</p>
<h3>真正的多智能体协作仍然混乱</h3>
<p>让多个智能体自由互相发消息、互相创建任务、互相管理，很容易变成混乱系统。实际更稳的方式仍然是经理与子任务模式：一个主代理拆分任务，多个子代理各自独立完成，再把结果交回。</p>
<p>每个子代理最好有独立机器和独立上下文，减少冲突。共享机器和自由协作听起来吸引人，但会带来状态冲突、责任不清和调试困难。</p>
<h3>智能体会反驳人类，是多智能体成熟的前提</h3>
<p>一个值得注意的变化是，智能体开始能对人类请求提出反驳。它不再只会顺从地执行，而是会判断某个修改是否合理。这种能力对多智能体协作很重要。</p>
<p>如果两个智能体掌握不同信息，它们需要能讨论、质疑、比较证据，并决定哪种实现更合适。如果所有智能体都只会附和，多智能体系统只会放大错误。</p>
<h2>十一、无审查 vibe coding 会让代码库快速劣化</h2>
<h3>两周左右就可能出现明显混乱</h3>
<p>Cognition 内部做过实验，让智能体连续开发真实产品，自动合并，不做代码审查。结果大约两周后，代码库就会明显变差。一个按钮颜色可能在十个地方分别实现，稍微改动就漏掉某处。</p>
<p>这种现象说明 AI 可以快速堆功能，但如果缺少审查和重构，代码结构会加速膨胀。速度越快，垃圾堆积也越快。</p>
<h3>代码库会向最差工程师的习惯退化</h3>
<p>如果团队中有人大量使用 AI 生成代码却不审查，坏模式会进入代码库。模型下次再写代码时，会把这些坏模式当成项目惯例继续学习。重复 helper、长 if else、局部补丁、风格不统一会逐渐扩散。</p>
<p>AI 时代的工程质量管理会更依赖边界控制。团队必须明确模块接口、架构规则、代码风格、可复用组件和禁止模式。否则模型会沿着已有混乱继续生成新的混乱。</p>
<h3>定期清理会成为必要流程</h3>
<p>重复代码和奇怪 helper 不一定要立刻消灭，有些重复在早期可以接受。但团队需要定期垃圾回收。可以由人类做，也可以让 AI 辅助查找重复实现、抽象公共函数、移除过时路径。</p>
<p>这类清理不能完全交给自动化，因为抽象边界需要判断。什么时候合并，什么时候保留局部重复，什么时候强制收敛，都属于架构层面的工作。</p>
<h2>十二、AI 代码味道和审查系统会成为新工具链</h2>
<h3>Agent written code 有自己的坏味道</h3>
<p>AI 生成代码常见问题包括重复实现、过度防御、局部修补、奇怪命名、无意义抽象、过长条件分支、只为通过测试而写的逻辑。它还可能 reward hacking，也就是用投机方式满足测试或提示目标。</p>
<p>这些问题不一定在功能层面立刻报错，但会损害长期维护。团队需要专门针对 AI 代码建立 lint 规则、Semgrep 检查、审查提示和结构性约束。</p>
<h3>审查重点要从语法转向结构</h3>
<p>AI 写出的代码通常能过语法检查，也能跑通局部测试。人类审查的重点应该放在结构层面：是否破坏模块边界，是否引入重复路径，是否绕开已有抽象，是否把临时方案写成长期逻辑，是否增加不必要复杂度。</p>
<p>AI 可以帮忙做第一轮，但人类需要守住项目的骨架。软件越大，这个职责越重要。</p>
<h3>保留为什么比保留改了什么更重要</h3>
<p>GitAI 这类方向尝试把变更背后的原因保留下来。代码本身只能显示改了什么，PR 说明和评论才能解释为什么这样改。</p>
<p>AI 参与越多，保留原因越重要。否则过几周后，人类和模型都只看到一堆变更，不知道当时的约束、权衡和上下文。高质量工程记录会成为 AI 时代的资产。</p>
<h2>十三、让公司变得 agent ready 本身就是工程改造</h2>
<h3>开发环境要可复现</h3>
<p>如果一个新人无法快速跑起项目，智能体也跑不起来。Agent ready 的第一步就是把开发环境整理清楚：依赖安装、环境变量、数据库初始化、服务启动、测试命令、常见故障处理，都要文档化和脚本化。</p>
<p>这不是为 AI 额外做事，而是补上工程管理欠账。AI 只是把这些欠账暴露得更快。</p>
<h3>测试路径要明确</h3>
<p>很多旧代码库没有可靠测试，或者测试只能由熟悉业务的人手动跑。后台智能体需要明确的验收路径，否则它只能猜。单元测试、集成测试、端到端测试、mock server、测试数据、录屏验证都会变得更重要。</p>
<p>AI 可以帮助补测试，但它首先需要知道什么叫正确。</p>
<h3>权限和数据访问要分层</h3>
<p>智能体可能需要读日志、查数据库、看工单、改代码、发 PR。每种操作都应有权限边界。生产数据最好只读，敏感密钥要作用域最小化，审计日志要可追踪。</p>
<p>后台智能体越有用，越不能随便放权。企业采用 AI 的关键不是大胆，而是边界清楚。</p>
<h2>十四、本地代理和云端代理会形成交接</h2>
<h3>Windsurf 2.0 代表前台到后台的连接</h3>
<p>本地代理适合快速互动、探索代码、修小问题。云端后台代理适合长任务、并行任务、需要等待测试或审查的任务。未来工作流会更像前台与后台协作。</p>
<p>开发者在本地发现问题，整理任务，然后交给云端智能体继续跑。云端智能体完成后返回 PR、测试视频和说明。本地与云端不是替代关系，而是工作阶段不同。</p>
<h3>开发者会更像工厂调度员</h3>
<p>Cursor 的说法是，AI 软件开发进入第三阶段：开发者不再主要写代码，而是在建造生产软件的工厂。这个工厂由一组代理组成，人类负责给方向、给工具、审查产物。</p>
<p>这会改变工程师技能结构。写代码仍然重要，但定义任务、拆分边界、配置环境、审查架构、设计测试和管理智能体，会变得更重要。</p>
<h2>十五、SRE、PM 和非工程角色也会进入代码流程</h2>
<h3>SRE 自动排障是自然场景</h3>
<p>后台智能体可以接入日志、监控、错误报告和代码库，自动做初步排障。比如某个服务报警后，智能体可以查最近部署、看相关日志、定位可疑 PR、生成修复建议，甚至开一个修复 PR。</p>
<p>这种场景适合智能体，因为它需要整合多源信息，并执行一套有规律的排查流程。人类 SRE 仍然负责判断风险和生产决策。</p>
<h3>PM 可以从 Slack 发起代码变更</h3>
<p>当后台智能体接入 Slack 和 GitHub 后，PM 或营销人员也能直接提出小型产品修改，让智能体生成 PR。比如改文案、调整页面、增加小功能、修复明显 bug。</p>
<p>这会让代码流程上游扩大。更多非工程人员可以发起变更，但合并仍然需要工程体系把关。否则代码库会更快混乱。</p>
<h3>始终在线的智能体像产品区域负责人</h3>
<p>一种更进一步的形态是，让智能体长期关注某个产品区域或 issue 集合。它定期整理优先级、提醒负责人、创建票据、追踪进展，甚至把部分任务交给其他智能体完成。</p>
<p>这让智能体从一次性执行者变成持续协作者。它不只是完成某个 PR，也能参与产品维护和任务管理。</p>
<h2>十六、AI 工程预算会继续上升</h2>
<h3>每个工程师每月上千美元的 AI 支出会变常见</h3>
<p>访谈中提到，企业可能为每位工程师投入 1000 到 5000 美元级别的 AI 预算。这个数字听起来高，但如果 AI 能带来更多合并 PR、更快排障、更少等待时间，对企业可能划算。</p>
<p>真正的问题是预算如何分配。前沿模型昂贵，子任务可以用较便宜模型。未来系统会混合使用 frontier 和 sub frontier 模型，把不同任务交给不同能力层级的模型。</p>
<h3>自治编码工厂会成为新的竞争方向</h3>
<p>当后台智能体、VM 基础设施、代码审查、测试视频、记忆系统、Slack 集成、GitHub 工作流和企业权限全部串起来，软件开发会越来越像自治工厂。</p>
<p>人类仍然在场，但位置变了。过去人类亲手搬砖，现在人类设计流水线、检查关键节点、处理异常和决定方向。真正有竞争力的团队，会把工程环境、测试体系、代码边界和智能体工作流一起建设起来。</p>
