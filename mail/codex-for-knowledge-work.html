Codex 正在变成知识工作的桌面操作台

E
Every，Dan Shipper，Austin Tedesco
2026-05-06
https://www.youtube.com

摘要

这期访谈讨论 Codex 如何从面向高级工程师的编程工具，转向知识工作者的日常工作入口。Dan Shipper 和 Austin Tedesco 重点展示了 Codex 在写作、增长、招聘、邮件、Slack、Notion、KPI 追踪和市场推广计划中的实际用法，核心判断是：能写软件的代理，也能重组知识工作。

内容框架与概述

第一部分围绕 Codex 的定位变化展开。Dan 认为，几个月前的 Codex 还像一个冷冰冰的高级工程师工具，主要用于结对编程，但随着模型能力和桌面应用体验提升，它正在变成知识工作的代理管理界面。关键变化不只是模型更强，而是代理能访问文件、浏览器、Gmail、Slack、Notion、Stripe 等工具，从而成为新的工作入口。

第二部分由 Austin 展示自己的实际工作流。他把 Codex 当作每天打开的第一个应用，大约八成工作时间都在里面完成。他用文件夹保存不同项目上下文，用密钥和项目说明连接公司系统，用审查代理检查战略一致性和数据准确性。他还展示了如何让 Codex 根据 Gmail、Slack、Notion 里的信息，自动头脑风暴可执行的工作流，比如未回复消息汇总、活动协调、招聘流程、邮件草稿和后续跟进。

第三部分重点讲复杂知识工作的代理化。Austin 用 Codex 整合会议转写、Slack 讨论和模板，生成市场推广计划，又用它在 Notion 中重建 KPI 跟踪器，让人和代理都能读取业务指标并据此行动。访谈也强调人工审核的重要性：代理负责生成、整理、草拟和执行，人则在 Gmail、Slack、Notion 等最终界面中确认内容，避免错误直接进入真实工作场景。

核心概念及解读

  • Agent Management Interface，代理管理界面
    指一种以桌面应用为中心的工作界面。用户不再直接在每个软件里手动操作，而是通过代理调度文件、数据源、网页、通讯工具和业务系统。它有点像新的工作台，重点不是聊天，而是派活、检查和交付。

  • Knowledge Work Coding Agent，知识工作编程代理
    访谈里的核心判断是，能写代码的代理本质上能调用工具、处理结构化信息、修改文件和执行流程。因此它不只适合工程师，也适合增长、招聘、写作、运营、数据分析等任务。

  • Compound Knowledge，复合知识工作流程
    Austin 从 Compound Engineering 借来多步骤审查思路，但把工程审查改造成知识工作审查。比如做市场推广计划时，不只检查代码安全或前端设计，而是检查战略一致性、数据可靠性、叙事逻辑和业务目标匹配。

  • Dumb Agent 与 Smart Agent，固定代理与智能代理
    固定代理适合每天重复做同一类任务，比如汇总未回复消息、生成邮件草稿、检查候选人进展。智能代理更像策略伙伴，适合和人来回讨论复杂问题，比如制定增长计划、产品发布方案、内容策略。

  • Agent Friendly Dashboard，面向代理的仪表盘
    KPI 表不只是给人看的报表，也要让代理能读懂。Austin 在 Notion 中重建 KPI 跟踪器，让代理能够读取订阅试用、页面浏览、产品指标和目标差距，然后据此建议行动，比如生成落地页或追踪 SEO 表现。

原标题 How to Use Codex for Knowledge Work
作者 Every，Dan Shipper，Austin Tedesco

访谈要点详情

一、总主题：Codex 不再只是编程工具，而是在变成知识工作的主界面

这期访谈最核心的判断是：如果一个代理能写软件，它就不只是会写代码，而是具备了处理文件、调用工具、组织信息、生成流程、执行任务的能力。换句话说，编程代理天然会越过工程边界，进入写作、招聘、增长、运营、数据分析、邮件处理、项目管理这些知识工作领域。

Dan Shipper 的判断很直接：几个月前的 Codex 还很难用，像一个给高级工程师配的结对编程工具，冷冰冰、强硬、缺少沟通感。但过去三个月左右，Codex 被重新塑造成一种桌面代理应用，能够访问文件系统、浏览器和各种工作软件，于是它从工程师工具变成了知识工作入口。

这里的关键不是 Codex 会聊天，而是它能在你的电脑里做事。它可以读 Gmail、Slack、Notion、Stripe 和内部数据源，可以生成文档，可以推送到 Slack，可以写代码，可以改产品，也可以帮你建立工作流。Austin 说自己每天登录后第一个打开的就是 Codex，大约 80% 的工作时间都在里面完成。

二、代理管理界面：新的知识工作操作系统

访谈反复强调一个概念：Agent Management Interface，也就是代理管理界面。它的意思不是单个聊天窗口，而是一种新的工作方式：你在一个桌面应用里管理多个代理，让它们去不同软件中执行任务、读取信息、生成结果，再把结果带回来。

Dan 的说法是，未来你如何工作、在哪里工作，会被这种代理管理界面重新规范。它有点像新的操作系统：以前你打开 Gmail 写邮件，打开 Slack 发消息，打开 Notion 写计划，打开数据工具看指标；现在你可能只打开 Codex，然后让它去这些地方处理事情。

访谈认为，这场竞争不只是 OpenAI 和 Anthropic 的模型竞争，而是每家公司都在争夺知识工作者的日常入口。Anthropic 有 Claude Code 和 Claude 桌面应用，OpenAI 有 Codex，Google 也可能会进入这个方向。谁的代理管理界面更顺手，谁就更可能控制用户每天工作的主界面。

三、Codex 与 Claude Code 的关系：从工程入口走向通用工作入口

Dan 提到，Claude Code 先证明了一件事：一个优秀的编码代理，如果足够快、聪明、有工具访问能力，就会自然扩展到非编程工作中。因为很多知识工作本质上也是处理信息、改文档、组织流程、调用工具。

这也是 OpenAI 后来调整 Codex 的背景。早期 OpenAI 可能把 ChatGPT 视为普通用户的氛围编程入口，把 Codex 视为高级工程师的受限编程工具。但 Claude Code 的成功让人看到，编码代理不该被限制在代码里，它本来就适合成为知识工作的通用代理。

Austin 的经历也印证了这一点。他最开始主要在 Claude Code CLI 中工作，用 Warp 做命令行入口，把它连接到工作和生活中各种系统。后来他开始试 Codex，发现 Codex 在桌面应用的速度、组织结构、子代理和自动化能力上更适合自己，于是逐渐把主要工作迁移过去。

四、Austin 的迁移经验：真正的阻力不是技术，而是心理习惯

Austin 说，很多知识工作者已经习惯 Claude Code 或 Claude 桌面应用，当他告诉朋友自己迁移到 Codex 时，对方会本能紧张，觉得是不是又要学一套新东西。但他的判断是，迁移并没有想象中困难，真正的门槛主要是情绪上的：人不愿意重新适应一个新工作台。

他认为 Codex 桌面应用比 Claude 桌面应用更快，组织结构更好，尤其是文件夹、持久聊天记录、项目上下文和工程友好性带来的体验差别很大。对他来说，Codex 的优势不是某一次回答更聪明，而是日常持续工作的摩擦更低。

这点挺重要。模型能力当然重要，但知识工作不是单次问答，而是一天十几个小时在工具之间来回切。哪个工具更快、更稳、更方便管理上下文，哪个工具就更容易变成主力。

五、文件夹、上下文和项目记忆：Codex 的组织能力是核心卖点

Austin 展示 Codex 时，最先强调的是文件夹和持久聊天记录。他会为不同工作创建不同文件夹，比如个人 Vibe Coded 应用、Every Growth OS、产品项目、KPI 跟踪器、Plus One 等。每个文件夹里保存着长期上下文、密钥、项目说明和审查代理。

这意味着 Codex 不只是一个临时问答工具，而是可以保存项目状态的工作空间。比如 Every Growth OS 文件夹里有关于公司业务、关注目标、协作方式、项目说明、内部工具连接的信息。Austin 可以在这个上下文中继续制定计划、调用代理、生成文档，而不需要每次从零开始解释。

这也是代理工作流和普通聊天的差别。普通聊天像一次谈话，代理工作流更像一个项目现场：资料、工具、历史、规则、人员角色都在里面。

六、Compound Engineering 到 Compound Knowledge：工程审查方法被迁移到知识工作

访谈里一个很有意思的点是，Austin 长期使用 Kieran Clausen 的 Compound Engineering 插件。这个插件原本服务于工程任务，会让模型在执行前规划、执行后审查，比如检查安全性、前端设计、代码质量等。

但 Austin 发现，很多知识工作也需要类似的多阶段审查，只是审查对象不同。比如制定市场推广计划时，安全审查不重要，重要的是战略一致性、数据准确性、业务目标匹配、叙事是否清楚、指标是否可靠。

所以他把 Compound Engineering 的思路改造为 Compound Knowledge，也就是面向知识工作的复合工作流。模型不再只问代码是否安全，而是检查计划是否符合公司目标、数据是否可靠、表达是否对目标用户有效。

这个点很值得拿出来看。AI 对知识工作的改造，不只是让它帮你写一段文字，而是把工程里的流程化、审查化、版本化方法搬到运营、增长、招聘、内容、战略这些领域。

七、自动化头脑风暴：让代理先告诉你它能为你做什么

Austin 推荐新人使用 Codex 的一个起点是：不要一上来就自己设计复杂提示词，而是让 Codex 查看你常用的工具，比如 Gmail、Slack、Notion，然后让它根据你的工作场景提出可自动化的流程。

他会让 Codex 进入一个项目文件夹，读取已有上下文，然后启动一种头脑风暴流程：看看我每天使用哪些工具，看看我有哪些重复劳动，想想哪些自动化流程能帮助我。Austin 认为，这比自己硬想更好，因为一个足够强的前沿模型可以反过来告诉你：你应该怎么使用它。

这里有个工作方式的变化：过去是人先想好流程，再让软件执行；现在是人把环境和目标给代理，代理反过来提议流程。它像一个懂工具的副驾驶，帮你发现你自己没意识到的自动化空间。

八、邮件、Slack、Notion 的自动化：从信息碎片中生成行动

Austin 举了很多跨工具自动化的例子。比如，在一天结束时，Codex 可以汇总他还没有回复的信息，生成回复草稿，然后由他审核和修改。它可以把流程图生成后推送到 Notion，再发送到 Slack。它可以检查合作关系、社交媒体营销、活动协调、招聘流程中的后续事项。

他的核心需求不是让 AI 写一封漂亮邮件，而是让 AI 处理分散在多个渠道中的工作碎片。知识工作者最累的地方，往往不是写，而是找、筛、归类、提醒、追踪、确认、复盘。Codex 的价值就在于把这些碎片变成可执行的下一步。

访谈里也提到 Kora 这个 AI 邮件助手。Austin 的建议不是直接让代理替你决定所有邮件规则，而是让代理先问你问题，理解你真正看重什么，再生成邮件过滤和回复规则。这样比用户自己拍脑袋写规则更可靠。

九、人类审核环节：代理可以生成，但最终发送要在人类界面确认

一个非常清醒的观点是：Austin 并不主张让 Codex 无脑代发所有消息。他喜欢把草稿和设置留在 Codex 里完成，但最终审核放在外部应用中，比如 Slack、Gmail、Notion。

他的理由很朴素：换一个界面审核，可以让大脑清醒一下。Codex 可以生成 Slack 消息草稿，但他会打开 Slack 的草稿区再确认。Codex 可以生成邮件草稿，但他会打开 Gmail 检查和修改。战略规划也一样，先推到 Notion 或 Markdown 文档，再做最后审查。

这不是保守，而是现实。代理负责跑腿、整理、草拟、推演，人负责最后一次判断。尤其是涉及客户、收入、招聘、公开发布这些场景，最后一步不能完全交出去。

十、傻瓜代理与智能代理：不是所有代理都要聪明

Austin 区分了两类代理。一类是 Dumb Agent，可以理解为固定代理或笨代理，它不需要很有创意，只要每次都做对同一件事。比如每天汇总未回复消息、生成邮件草稿、整理任务提醒、检查某类状态。

另一类是 Smart Agent，更像创意战略合作伙伴，适合来回协作，比如制定增长策略、构思产品发布、分析复杂业务问题、设计新流程。Austin 认为 Codex 擅长搭建这两类代理。

这个区分很实用。很多人误以为代理越聪明越好，但真实工作里，大量价值来自稳定重复的小动作。一个每天靠谱整理邮件和提醒的固定代理，可能比一个偶尔灵光一闪的超级代理更有用。

十一、多个专用代理优于一个万能代理

Austin 受到 Claire Vo 访谈的启发：不要把所有任务都塞给一个超级代理，而是建立多个有明确职责的专用代理。他把这套思路用于增长工作，在 Slack 中部署了六个代理。

这些代理有些是固定执行重复任务的自定义代理，有些则更智能，负责更开放的策略或判断。Austin 认为，这种拆分方式比一个万能代理更稳定，也更容易调试。

这里的道理跟组织管理很像。一个人负责所有事情，很快会混乱；把职责拆清楚，哪怕每个角色不完美，系统也更容易运转。AI 代理也是这样，边界清楚比能力膨胀更重要。

十二、代理也会犯错，但 Codex 可以用来修代理

Austin 很坦率地说，代理仍然会出错，尤其是在公开通话、个人代理和复杂工作流里。关键不是幻想代理不会犯错，而是建立修复机制。

他的方法是，当 Slack 里的某个代理出现问题，不是继续和它纠缠，而是打开 Codex，截图或者找到相关对话，让 Codex 定位问题并修复代理架构。也就是说，Codex 不只是使用代理的地方，也是调试代理的地方。

这点很关键。未来知识工作者可能不只是使用 AI，而是维护一组自己的工作代理。就像今天工程师调试代码，明天知识工作者可能调试自己的信息流、邮件代理、招聘代理、写作代理。

十三、市场推广计划：从会议转写和 Slack 讨论生成 GTM 方案

访谈后半段展示了一个 Austin 最喜欢的知识工作用法：把会议转写、Slack 讨论、内部上下文、产品信息丢给 Codex，让它综合生成 Go To Market 计划，也就是市场推广计划。

这类任务过去非常耗人。你要读会议记录、翻 Slack、理解产品背景、抓住用户痛点、组织叙事、写出计划、再和团队沟通。Codex 的价值在于，它可以把这些散乱材料合并成一份结构化方案。

这不是单纯写作，而是综合信息。它要做的事包括读取资料、提取共同主题、识别业务目标、形成行动步骤、生成文档，再进入审查环节。访谈把它作为 Codex 进入复杂知识工作的典型案例。

十四、KPI 跟踪器：给人看，也给代理看

Austin 说自己很喜欢用 Codex 每周重建 KPI 跟踪器。他们的业务涉及多个方面，数据分散在不同来源里。传统工具可以做数据汇总，但他想在 Notion 里重建一套既适合人类查看，也适合代理读取的 KPI 表。

这套 KPI 表会包括新的付费订阅试用、页面浏览量、Monologue iOS 相关指标，以及和计划的对比。这样做的目的不是为了好看，而是让代理能基于可靠指标行动。例如，如果代理发现某个关键词 SEO 表现低于预期，而且数据源可靠，它就可以建议或生成一批落地页来争取流量。

这背后是一个很重要的观念：未来很多内部文档、表格、仪表盘，不只是给人类员工看的，也要给代理读。文档结构、指标命名、数据准确性，都会直接影响代理能不能干活。

十五、数据准确性：代理越能行动，数据越不能含糊

Austin 在 KPI 表这部分很强调数据准确性。他说，Codex 一次性生成 KPI 表时，格式、数字、框架可能会有 5% 到 10% 的误差。但业务数据不能有这种误差，甚至 3% 的错误都可能无法接受。

所以他采取了一个看似笨但必要的方法：逐列检查，确保每一列都完全正确。只有这样，团队才能放心让代理根据 KPI 表采取行动。

这句话很扎实。AI 越像员工，数据地基越重要。一个不会行动的报表错一点，最多误导判断；一个会自动行动的代理读错数据，就可能直接造成业务损失。

十六、招聘：用 Codex 扩展候选人搜索和背景判断

Dan 也提到自己用 Codex 做招聘。他们要招一位学习与发展负责人，需要能帮助公司做课程的人。他想到 General Assembly 这类曾经做过技术教育、编程、设计课程的机构，于是让 Codex 帮忙寻找相关人才线索。

这个例子说明，招聘并不只是发布职位和筛简历。高质量招聘往往需要反向思考：哪些公司培养过类似人才，哪些人可能有相关背景，哪些经历对应岗位能力。Codex 可以帮助把这种模糊搜索变成结构化研究。

在这种场景里，代理的作用不是替人拍板，而是扩展搜索半径、生成候选名单、整理背景信息、找出可能路径。人最后仍然负责判断候选人是否合适。

十七、产品设计变化：代理会削弱传统控制面板和 onboarding

Dan 讲到 Plus One 的例子。以前一个产品要让用户完成设置，往往需要完整的控制面板、引导流程、表单、按钮和上下文收集。但如果用户已经有 Codex 或 Claude Code 这样的代理，产品就可以通过 CLI 或 API 暴露给代理，让代理直接和用户对话，并从用户电脑、历史对话和文件中获取设置所需的上下文。

这会改变软件产品的设计。过去 SaaS 设计的核心是界面、仪表盘、按钮、表单；代理时代，很多产品可能更像工具接口和能力模块。用户不一定亲自点按钮，而是让代理完成配置。

这和你之前聊的 SaaS 破产逻辑有点接近：不是软件消失，而是传统 SaaS 的界面中心地位下降。未来产品可能需要优先考虑代理能不能调用、能不能读取、能不能自动配置。

十八、Codex 的优势：速度、组织结构、工程能力和自动化能力

Austin 对 Codex 的喜爱主要来自几个方面。

第一是速度。他认为 Codex 桌面应用很快，用起来有一种难以放弃的顺滑感。第二是组织结构，它支持文件夹和持久上下文，比纯聊天应用更适合长期项目。第三是工程友好性，它可以直接处理 PR、产品代码和项目文件，不需要在不同工具之间切来切去。第四是子代理和自动化，它会主动推荐并创建工作流。

这说明 Codex 的竞争力不是单点模型智商，而是模型、工具访问、项目组织、执行速度、长期上下文、工作流管理的组合。

十九、访谈里的隐含判断：知识工作会越来越像工程工作

这期访谈表面上讲 Codex，背后更大的判断是：知识工作会被工程化。

以前写作、增长、招聘、运营、战略这些工作，很多依赖个人经验和松散流程。现在它们开始变成可拆解、可审查、可版本管理、可自动化、可代理执行的流程。

比如市场计划可以有审查分支，KPI 表可以被代理读取，邮件可以生成草稿并进入人工审核，招聘可以转成候选人搜索流程，Slack 里可以部署多个专用代理。知识工作不再只是脑子里想一想、文档里写一写，而是逐渐变成一套可运行的系统。

二十、这期访谈最核心的几个判断

第一，编码代理的边界会自然扩展到知识工作。因为写代码需要的能力，本质上就是读写文件、理解上下文、调用工具、修改系统、验证结果。

第二，桌面代理应用可能成为新的工作入口。你不再从一个个应用开始工作，而是从代理管理界面开始工作。

第三，多个专用代理比一个万能代理更现实。固定任务交给固定代理，复杂任务交给智能代理，这比幻想一个超级助手解决所有事更靠谱。

第四，AI 工作流必须保留人工审核。尤其是邮件、Slack、客户沟通、招聘、业务数据和公开发布，最后一步最好在人类熟悉的外部界面确认。

第五，数据结构会变得比以前更重要。因为代理要读你的 KPI、文档、任务和历史上下文。资料越清楚，代理越能干活；资料混乱，代理就会放大混乱。

第六，软件产品会从界面优先转向代理可调用优先。控制面板、引导流程、手动配置会减少，CLI、API、Markdown、Notion 数据库、代理可读文档会变得更重要。

第七，知识工作者未来不只是使用 AI，而是管理一组代理。你要知道哪些任务适合自动化，哪些任务必须人工检查，哪些代理该拆分，哪些代理出错后该如何修复。

二十一、可以提炼成一句话

这期访谈讲的不是 Codex 会不会写代码，而是：当一个编码代理能读你的工具、懂你的上下文、能生成流程、能调用软件时，它就开始接管知识工作的操作层。人的工作不会立刻消失，但会从亲自操作软件，转向设计流程、检查结果、维护代理和判断方向。
